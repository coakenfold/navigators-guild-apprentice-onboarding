Design doc companion · 02 Tracking your work

tracker, screen by screen

The same tool as DESIGN.md, shown as a sequence of terminal sessions instead of tables. It follows a week of work on a small bookmarks app. You set things up and plan the work. An agent picks up items, does the work, and submits. The tool decides what reaches done and what waits for you.

You at an interactive terminal Agent Claude Code running shell commands donereviewrefused where each item ends up

Tracker version. This page shows tracker 0.1.0 built from commit e5dbdd4 (TR-57), which has all 16 slices of PLAN.md and their review fixes. Every tracker command and line of its output was captured on 2026-11-24 by running that build against a throwaway store and a small Node bookmarks app. Long outputs are trimmed where you see …, and paths are shortened to ~.

Two stand-ins. npx playwright test runs the app's node:test tests with a Playwright-style reporter. tracker-judge answers from a script instead of calling claude-haiku-5-5, so you can see a wrong pass, an unsure answer and a wrong fail on cue. Its reasons are written in the style of the real model's answers in judge-eval/results/claude-haiku-5-5.json.

One sitting. The story spans a week, but the run took minutes, so the timestamps are minutes apart. They're in UTC, which is why they read 2026-11-25. To show an overdue digest in scene 8, review.digest.every_days was set to 0 for that one command.

Setting up

Done once per project.

01You

Register a project

One store in ~/.tracker holds every project. A project needs a key, a name and a root to start. project add writes those to config.json, and you add the checks and review policy there by hand.

  • The root can be the top of a git repo or a folder inside a larger one, such as one package in a monorepo. Either way, the gates and triggers look only inside it.
  • Project checks run on every submit (G4), whatever the item is about.
  • source_paths adds *.js to the src/** default, because this app keeps app.js at the top level and the rest of its code in src/. It decides which files count as source code, so adding a new one holds the item (T1).
  • There are no judge settings here. Judges run only for items whose criteria ask for one, and the defaults do: the command is tracker-judge and the model is claude-haiku-5-5, chosen by comparing models on judge-eval's labelled cases. Its latest run, 54 cases through tracker-judge, gave 52 correct, 2 unsure and no wrong passes.
  • Two lines in Claude Code's settings let agents run tracker without asking you each time, and stop its edit tools from touching the store.

02You

Turn a plan into items

A couple of weeks in, BM-1 to BM-11 already exist. A /decompose plan gives you three new slices. Each slice's outcome becomes a title, and its "Done when" lines become criteria.

  • You write criteria in your own words. The agent gives them checks in the next scene. Each text is saved in the item's written list, and rewording or dropping one holds the item (T5).
  • Every new criterion is manual until it gets a check or a judge, and create says how to give it one.
  • Running from inside ~/code/bookmarks makes BM the default project, so there's no --project, and list shows only BM. --all shows every project.
  • list sorts high before medium before low, and hides done and shelved items unless you ask for them.

03Agent

Write failing tests, then start

Following the instructions in CLAUDE.md, the agent reads the item, turns each manual criterion into a script check, writes the tests those checks run, commits them as test(BM-12): …, and starts.

  • start runs every check once and expects it to fail, because the feature doesn't exist yet. It warns about one that already passes, and that one holds the item at submit (T13, scene 12).
  • It records each result, the commit HEAD pointed to, and a fingerprint of the criteria under Started: in show (scene 6). Changing the criteria after this point holds the item (T5).
  • "Failed at start, passed at submit" is what makes a check mean something.
  • Every criterion has a check, so T6 will stay quiet and nothing here will need you.

04Agent

Ask "what's left?"

The agent writes the code, commits with the item ID as the scope of each message, and runs gates. This dry run shows what a submit would refuse, without changing anything. It finds two problems at once.

  • Every problem is listed at once, so the agent can fix them in one pass. The checks run even though G5 failed. Only judges wait until every other gate passes, so a broken test never costs a model call.
  • G5: everything under the project root must be committed, including no untracked files, so the commit holds everything the tests ran with. Files outside the root don't count.
  • G4: BM-12's own checks pass, but the project's full suite doesn't. The new code broke "persists across reloads", which BM-10 already took to done. Project checks run on every submit, and that's what stops later work from breaking done items.
  • The failure shows the command, the exit code and the last lines of output, so the agent can go straight to the cause.
  • The scope in feat(BM-12): … is how the tool finds this item's changed files. A commit since start that touches the project but has no item scope would hold the item (T14).

05Agent

Fix the regression the suite caught

persistence.spec.js is BM-10's proof. The agent finds the cause in its own code, fixes it, and runs gates again.

  • The fix is in the code, not the test. Changing BM-10's test would hold the item for you (T4), and the test is right.
  • With every gate passing, gates also runs the triggers and lists any hold a submit would get. There's none, so none is listed.
  • BM-12's criteria are all tests, so no judge runs and the model is never called. Judges run only for items whose criteria ask for one (scene 9).
  • A refusal changes nothing. BM-12 stayed in progress the whole time, and nothing here needed you.

06Agent

Submit: auto-verified

Every gate passes and no review trigger fires: no new file, no new dependency, no test edited, criteria unchanged since start. The item goes straight to done with nobody asked.

  • No judge ran. Both criteria are tests, so BM-12 reached done without the model.
  • The verification record is the proof: which commit, which checks, and what they printed. An item with a judge also records each answer and the model that gave it.
  • Each check's last lines of output are saved at done, so the record shows which tests actually ran, not what anyone claims ran.
  • Started: shows both checks failed at start. With the record, that's "failed at start, passed at submit".
  • refs/tracker/BM-12 keeps that commit, even if its branch is rebased or squashed, so the tests as they ran can still be read.
  • You'll see BM-12 later in the digest, not now.

When the tool wants you

Gates passed, but something risky happened.

07Agent

A risky change is held

BM-14 adds fuzzy search with a new library and edits an existing test. The work passes every gate, but two triggers fire, so the item waits for you.

  • A held submit still exits 0. Being held isn't an error; the output says where the item ended up.
  • The triggers come from git history, not from what the agent says: package.json, package-lock.json and a file under tests/ are among BM-14's changed files.
  • T4 counts the item's own test(BM-14) commit, even though it came before start, and says so.
  • An edited test may no longer prove the done items that relied on it, which is why T4 holds. G4 already ran the full suite, so nothing done is broken: what you check is whether the edit weakened a test.
  • The agent can't approve its own work. It stops and reports.

08You

Clear the inbox

tracker review is the one command you need to remember. It lists what's waiting and why, and flags a digest you haven't read in time. You read BM-14's change with show --diff and approve it.

  • show --diff lists the files that fired a trigger before the commits and their diffs, so you know what to read first.
  • approve shows the holds again and asks you to type the item ID. That needs an interactive terminal, which an agent's shell isn't.
  • Then it runs the gates again at HEAD, so nothing that broke since the submit gets through.
  • Deciding BM-14 also frees the project. Only one item at a time can be in progress or in review (G1), so BM-13 couldn't start until now.

09AgentYou

A judge for what tests can't measure

BM-13's first criterion is a normal test. Its second asks whether every import error is helpful, which a script can't decide. So the agent writes a judge: two short yes/no questions, asked once for each error in src/import.js. One answer comes back unsure, and you send the item back with a concrete note.

  • each splits the work in code: one request per match, two questions each, and every answer must pass. A pattern that matches nothing is refused, because a judge with nothing to grade would pass without asking anything.
  • The judge runs at start too, against the old 'Invalid file.' messages. It should not pass yet. If it did, its questions couldn't tell bad messages from good ones (T13).
  • Unsure means the excerpt doesn't show enough to decide. It's not a confidence score. In judge-eval's run of claude-haiku-5-5, 2 of 54 answers were unsure and none was a wrong pass. Unsure isn't a fail, so the gates pass. It's not proof either, so T10 holds the item.
  • The excerpt and the model's reason come with the hold, so you can decide without opening the file.
  • Your reject covers this submit only. v1 saves no rulings, so if the agent resubmits the same code, the cached unsure answer holds it again.

When the judge is wrong

The model fails good work, and the agent can't overrule it alone.

10AgentYou

Dispute a wrong fail

The agent reworks BM-13 using your note. Instead of repeating the next step in every message, importMessage() in app.js now adds it after every row error, so the message at :26 only names the problem. The judge sees a few lines around :26, not app.js, and answers no to suggests_next_step, confident and wrong about what the user sees. The agent can show it's wrong, so it disputes the answer.

  • A fail refuses the submit. Without disputes, that would be a dead end, because the item could never reach review.
  • --dispute can't pass anything. It moves the decision from the model to you, under T12, with the model's reason and the agent's side by side.
  • A judge sees only its excerpt. A next step that lives somewhere else, here in app.js, is exactly what it can miss.
  • Answers are cached by content, so the unchanged excerpts at :11, :15 and :18 aren't asked again, and neither is :26 on the disputed submit or the approve.
  • Your approval covers this submit only. v1 saves no rulings, so if BM-13 ever comes back with the same code, it needs the same dispute.
  • Your decisions count toward tracker judges. If suggests_next_step keeps getting overruled, the question itself needs fixing.

11You

Audit the digest

Each project's digest lists everything that reached done without you since you last acknowledged it, then every shelve and human action since. Items that passed on a judge come first, because that's where a wrong pass is most likely.

  • BM-11's judge said yes to both questions, and it was wrong: "Nothing here." isn't friendly. An answer carries no measure of doubt, so a wrong yes looks like any other (§7). judge-eval found no wrong pass in 54 cases, but the CLI has no temperature setting, so a rerun can answer differently. That's why the digest exists.
  • Your own approves and rejects are listed too, marked from a terminal or not. The terminal check can be got around, so you check that you really made each one.
  • reopen sends BM-11 back with your reason. If it comes back with unchanged code, T13 holds it, because its check and judge already pass at start (scene 12). The better fix is a test instead of a judge.
  • Outside every project root, tracker digest shows every project's digest. digest ack shows the digest again, asks you to type ack, and resets the overdue clock. BM-11 is open again, so the ack counts 2 items, not 3.

12YouAgent

Guardrails in action

Short exchanges from across the week where the tool says no, or lets something through but makes sure you'll see it. Most map to a row in the trust table in §6.

  • An agent can't approve, reject, delete or acknowledge a digest. Each needs a human typing at a terminal.
  • Moving the goalposts is allowed but never quiet. Neither criterion set nor criterion remove warns about it, but gates lists the T5 hold once the gates pass, and the submit is held. That includes dropping one of your criteria before starting.
  • A check that passes before the work is allowed but flagged (T13). cargo test with a filter that matches nothing exits 0, which is the classic case.
  • A dispute only works on a question that actually failed, so it can't be filed in advance.
  • Shelving work that's under way must leave the project checks passing. The item's tests still fail, and left on the branch they'd fail the next item's submit (G4), so the agent reverts them first.
  • Only you can delete, and the prompt says what goes with it. An item that won't be done is shelved by the agent, then deleted by you.
  • audit catches a hand-edited status after the fact. It can't prevent one.

The agent's view

One item from prompt to done, as Claude Code runs it.

13Agent

One whole session

You give one instruction. Every call after it is the agent's, through Claude Code's tools. The only thing you read is the report at the end.

  • The allow rule means none of these calls needs your approval.
  • --json gives the agent fields to act on: the criteria, the start results, and each failure's gate, command, exit code and output, plus ref, answer and reason when a judge fails. The progress lines go to stderr, so stdout is one JSON object.
  • Both criteria can be tested, including the toast text, so no judge. Judges are for what a test can't measure.
  • When it reaches for the item file to tick off a criterion, the deny rule stops it. Nobody ticks criteria: the checks prove them at submit.
  • The full suite (G4) catches an existing test the feature broke. Changing that test would hold the item (T4), and the test is right, so the agent fixes the code.
  • Every trigger's fired is false, so BM-17 auto-verified, and you'll next see it in the digest.

What the mockup surfaced

Decisions it settled

This page began as a mockup, written before the tool existed. Writing concrete screens exposed twelve gaps in the design doc, and planning the build exposed one more. Each one was decided in DESIGN.md, and the screens above show the build that came out of it.

A judge that fails good work is no longer a dead end

The agent can dispute the fail, which holds the item for you under T12. Your approval decides that submit, and tracker judges counts it against the question (scene 10).

§2.3.2 · T12 · §2.7

A wrong pass can't come back unchanged

reopen sends a done item back with a reason. If it returns with unchanged code, T13 holds it, because its checks or judge already pass at start (scene 11, scene 12).

§2.6 · T13

The check is the evidence

Script and judge criteria need no evidence note: their own output is the proof, saved at done. Only a manual criterion gets a note, and it's left out of the T5 fingerprint because it can only be written once the work exists (scene 6).

§2.3 · G2 · T5

The inbox shows the change

tracker show <ID> --diff lists the item's commits and diff, with the files that fired a trigger named first, so you never leave the tool to review a hold (scene 8).

§3 Looking around

Triggers are re-checked on every submit

After a reject, the resubmit is held again for every trigger that still applies, because the work changed since you looked. None of your earlier decisions carry over.

§2.5

The record shows which tests ran

Each check's command, result, duration and last 20 lines of output are saved at done, so tracker show prints what actually ran. refs/tracker/<ID> keeps the commit through rebases, and G5 refuses untracked files, so the commit holds everything the tests ran with (scene 6).

§2.3 · G5 · §2.7

Checks must fail before the work

start runs every check and expects a fail. One that already passes, like a filter matching no tests, holds the item under T13 (scene 3, scene 12).

§2.4 · T13 · §5

Changing a proving test is visible

T4 ignores pure additions and holds any change to an existing test, because it may be another item's proof. G4 runs the full suite on every later submit, so a change that breaks done behaviour is refused (scene 4, scene 7).

T4 · G4 · §6

Your criteria can't be quietly rewritten

The criteria text is saved in written at create. An agent can attach checks and add criteria, but rewording or dropping yours holds the item (T5), even before start (scene 12).

§2.1 written · T5

Judges must have something to grade, and must not pass yet

A judge whose pattern matches nothing is refused instead of passing empty. Criterion judges also run at start, and one that already passes is held like a check that does (scene 9, scene 12).

§2.3.1 · §2.4 · T13

Agents never edit tracker files

Items change only through tracker commands. Claude Code's settings allow tracker without asking and deny its edit tools on the store (scene 1, scene 13).

§3 Interface · §5 settings

Output agents can parse

Every command takes --json. The text can change freely, but the JSON fields are an interface, with refs and hold reasons as data, each checked against a schema in schemas/ (scene 13).

§3 Output for agents

A project can live inside a larger repo

A root can be a folder in a bigger repository, such as one package in a monorepo. G5, T14 and the path globs look only inside the root, so a dirty file or an unscoped commit elsewhere in the repo doesn't refuse or hold the item. The price: a change to a file outside the root that the tests read isn't caught (scene 1).
