## Verdict

Slice 9 does what the plan asks. `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo clippy --all-targets -- -D warnings` and all 327 tests pass, the count and the per-file split the readme gives. Every _Done when_ bullet has a test, apart from the by-hand half of the fourth, and each of TR-5's eight checks runs one module of [tests/review.rs](../../tests/review.rs), matching 3, 1, 2, 3, 3, 1, 1 and 1 tests in the record's saved output.

- **`approve`'s re-read under the lock is sound.** It reads the item and its file's text before the question, then compares the file with those same bytes twice under the lock: once after the question ([main.rs:3095](../../src/main.rs#L3095)) and once after the checks ([main.rs:3101](../../src/main.rs#L3101)). Anything written to the file in between, by a check, an agent or a second `approve`, makes it exit 1 with nothing written, and the ref is set only after both. It runs submit's gates in submit's order, so it gets G5's flag checks and the second look. `approve_writes_nothing_when_a_check_edits_the_item_file` covers the second compare. One gap: nothing tests its second look at the tree (test gap 1).
- **No item is held wrongly or stuck by this slice's code.** T6 and T9 read only the item, which the re-read pins. An agent can't take a held item out of review: `edit`, the `criterion` commands and `evidence` refuse it from piped stdin (I ran `edit` and `evidence` to check), and `approve` and `reject` need a terminal. `reject` always works on a held item, even when `approve`'s gates fail or the project's root is gone, so nothing is stuck for good.
- **TR-5 was tracked as the rules ask.** Its tests were committed 28 seconds before `tracker start`, all eight checks failed at start, every commit is scoped to it, and the installed slice 8 binary verified it `auto` at `10e519a` with `refs/tracker/TR-5`. Nothing could hold it, since that binary has no triggers.

The findings that matter most:

- **Design 1:** `approve` verifies at whatever `HEAD` is there when it runs, and doesn't run the triggers again. So commits made after a held submit are approved with holds that never looked at them, and neither the question nor the record says so. I reproduced it with an unscoped commit adding `Cargo.toml`. It's harmless now, but slice 10's and 11's triggers make it matter, and the agent's own workflow commits after its submit.
- **Design 2:** the `gates` dry run lists no triggers or holds, though §3 says it does, so an agent can't learn from a dry run that its submit will be held.
- **Process 1:** typing the ID into `approve` and `reject` in a real terminal hasn't been tried. Slice 10 is the first slice whose item can be held, so this should be checked before it starts.

## Bugs

1. **The inbox's heading says "it" for any number of items.** [main.rs:3011-3013](../../src/main.rs#L3011-L3013) prints "{count}, waiting for you to approve or reject it:", so two held items read "2 items are held for review, waiting for you to approve or reject it". The readme found it and shows it in its demo ([slice-9-readme.md:343](../slice-9-readme.md#L343)). It's certain to show whenever two items are held, and it's only text: the JSON doesn't have it. Fix: end the heading "…, waiting for you to approve or reject each one:", which reads for one item too.

2. **`show --diff` outside a git work tree says tracker can't "record or prove" the work, though `show` only reads it.** [commits_and_patches](../../src/main.rs#L2689-L2704) calls `git::require_work_tree` ([git.rs:69-74](../../src/git.rs#L69-L74)), whose message is written for `submit` and `start`: "isn't inside a git work tree, so tracker can't record or prove PL-1's work against a commit. … Nothing was changed." The readme found this too ([slice-9-readme.md:346](../slice-9-readme.md#L346)). The exit code, 3, is right, and the advice to `git init` still fits, so it's a small wording problem, and an unlikely one, since a project outside git can't submit anything either. Fix: **(a)** have `commits_and_patches` map the error to "Can't show PL-1's commits: PL's root, …, isn't inside a git work tree.", as it already does for a missing root. **(b)** Give `require_work_tree` a phrase for what the caller wanted. I'd pick (a): it changes one caller and matches the line above it.

## Security

1. **`show --diff` applies textconv filters, so the diff I review can hide lines that the commit holds.** [git::patches](../../src/git.rs#L240-L270) passes `--no-ext-diff` but not `--no-textconv`, and `git show` runs a `diff.<driver>.textconv` command on any file whose attributes name that driver. The driver is set in `.git/config` and the attributes can come from `.git/info/attributes` or `core.attributesFile`, none of which any commit shows.

   Reproduced in a temporary store: the commit added `xx/work.sh` with two lines, one of them `rm -rf the_tests # hidden`, and `xx/.gitattributes` with `*.sh diff=quiet`. After `git config diff.quiet.textconv "grep -v hidden"`, `tracker show XX-1 --diff` printed `@@ -0,0 +1 @@` and only `+ok line`, while `git show --no-textconv` printed both lines.

   It's deliberate only: no honest agent sets a textconv to fool its reviewer, and one that can write `.git/config` can already run anything. But `show --diff` is the screen I read before approving a held item, and a deceiving diff leaves no trace in history, which is worse than the commit-level dodges §7 lists. Fix: add `--no-textconv` to `patches`' arguments, beside `--no-ext-diff`, and a test that a textconv driver doesn't change the diff. It's one flag.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **`approve` verifies at whatever `HEAD` it finds and doesn't run the triggers again, so commits made after a held submit are approved without any trigger or question naming them.** A held submit records no commit ([main.rs:2246-2251](../../src/main.rs#L2246-L2251)), and `approve` sets `commit` and the ref at the `HEAD` its own G5 sees ([main.rs:3095-3105](../../src/main.rs#L3095-L3105)), as `10e519a` wrote into §2.7 ([DESIGN.md:360](../DESIGN.md#L360)). Its question shows only the holds from the submit, and `verification.triggers` copies them ([main.rs:2412](../../src/main.rs#L2412)). The readme chose this ([slice-9-readme.md:584](../slice-9-readme.md#L584)), and `approve_typed_in_a_terminal_moves_the_item_to_done` commits while the item waits on purpose. §2.5 says the triggers look at all of an item's commits on every submit, but §2.7 doesn't say whether `approve` does, so the code had to guess.

   Reproduced in a temporary store: XX-1 was held under T6 at `780c8e6`. I then committed `xx/Cargo.toml`, unscoped, as `wip: sneak a dependency in while held`, at `32e75de`. Typing `XX-1` into `approve` under `script` showed only "T6  criterion 1 is manual", and the record says `by: "human"`, `commit` `32e75de` and `triggers` `[T6]`. `show --diff` wouldn't have shown that commit either, since it's unscoped.

   In this slice it's harmless: T6 and T9 read only the item, and the re-read pins it. From slice 10 it matters. T3 would have fired for that `Cargo.toml` and slice 11's T14 for the unscoped commit, but they never run on it, and the record says I approved a commit whose triggers I wasn't shown. It's also likely: the agent's workflow commits after its submit. `4c19e71`, PLAN.md's "in review", came 4 seconds after TR-5's submit, and the readme's commit is unscoped. Fix, in slice 10 once triggers read commits: **(a)** `approve` runs `triggers::run` before asking, at the `HEAD` it will name, shows every hold that fires there with the new ones marked, records those in `verification.triggers`, and exits 1 with nothing written if G5's `HEAD` isn't the one the question named. §2.7 then says so. **(b)** A held submit records its `HEAD`, and `approve` refuses with exit 1 if `HEAD` has moved under the root since then, saying to reject so a resubmit works the triggers out again. **(c)** A §7 line only. I'd pick (a): (b) would refuse nearly every approve, because of the agent's own commits after a submit, and (a) shows me what I'm approving without a reject and resubmit.

2. **The `gates` dry run lists no triggers or holds, though §3 says it does.** §3 says "For `gates` and `submit`, the object lists … `triggers`: every trigger that ran … `holds`: the triggers that fired" ([DESIGN.md:467-471](../DESIGN.md#L467-L471)). [gates_dry_run](../../src/main.rs#L1820-L1849) prints only `id`, `status`, `result` and `gates`, and [gates.schema.json](../../schemas/gates.schema.json) allows nothing else. Reproduced: `gates XX-1 --json` on an item with a manual criterion printed five passing gates and nothing more, and the `submit` after it was held under T6.

   Before this slice there were no triggers to list, so the gap first matters now. §2.4 calls `gates` the agent's way to ask "what's left?", and an agent that runs it can't learn that its submit will be held, which the brief tells it to stop and report. Fix: **(a)** once every gate passes, `gates_dry_run` runs `triggers::run` and adds `triggers` and `holds`, with the text naming any hold, and `gates.schema.json` gains both. **(b)** Change §3 so that only `submit` lists them. I'd pick (a): it's a few lines, and slice 10's triggers make the dry run's answer more useful still.

3. **§4.3's example `auto` record has `"triggers": []`, which this slice's own bullet says an `auto` record never has.** [DESIGN.md:637](../DESIGN.md#L637) shows `"triggers": []` in a done item verified `auto`, and the bullet `10e519a` added says `verification.triggers` "a `human` record keeps and an `auto` one never has" ([DESIGN.md:687](../DESIGN.md#L687)). The code leaves the field out when it's empty ([item.rs:125-128](../../src/item.rs#L125-L128)), so no file looks like the example. It's only the example. Fix: drop the `"triggers": []` line from it.

## Test gaps

1. **Nothing tests `approve`'s second look at the tree.** With `gates::tree_after_checks` deleted from `approve` ([main.rs:3100](../../src/main.rs#L3100)) in a copy of `657559b`, every test still passes, apart from `docs_links`' `line_anchors_name_lines_that_exist`, which needs the repository's history and fails in any copy, as the readme says. Without that call, a check that leaves an untracked file under the root, or moves `HEAD`, lets `approve` record a `human` verification at a commit the checks didn't run against. That's what §2.4's "Checks leave the tree as they found it" is there to stop, on the path a held TR item takes from slice 10 on. Fix: a test beside `approve_writes_nothing_when_a_check_edits_the_item_file`, modelled on [commits.rs:1032](../../tests/commits.rs#L1032)'s `gates_fails_g5_for_a_file_the_checks_leave`: a criterion check that writes `xx/left.txt` once a marker outside the repo exists, the marker made after the held submit, then `approve` under `script` exits 2 with G5, the item stays in review, and there's no ref.

   A second mutant, with `approve`'s first re-read ([main.rs:3095](../../src/main.rs#L3095)) changed to a plain `store.lock()`, also passes every test. That one is almost harmless: the second re-read compares with the same bytes, so a change while the question waits is still caught, only with "changed while its checks ran". So the re-read is sound without a test for its first half.

2. **The cases the readme lists as untested are untested, and one of them guards a worse failure than it suggests.** The readme names `review`'s line for a held item with no `holds`, `show --diff` for an item with no commits and its exit 3, and `reject` cancelled or changed while the question waits ([slice-9-readme.md:515](../slice-9-readme.md#L515)). I confirmed none has a test. The `reject` re-read ([main.rs:3171](../../src/main.rs#L3171)) matters most: without it, a reject typed in one terminal while I approve the item in another would move a done item back to in-progress, keeping its `verification`, which §2.1 says is present only while the item is done. The code is right now. Fix: a `reject` test whose `meanwhile` closure appends to the item file, as `delete`'s tests do, asserting exit 1 and the file unchanged, and one with a wrong ID. The other three are display paths, worth a test each but low risk.

3. **No test checks a passing `approve --json`, or its exit 2 refusal, against a schema.** `approve.schema.json` is never exercised: the `script` tests read the file afterwards, not the output, and the only `approve --json` run is the piped refusal ([review.rs:370](../../tests/review.rs#L370)). I ran both by hand in a temporary store: the refusal had `error`, `exit_code: 2`, `id`, `status: "review"`, `result: "refused"`, `gates` and `failures`, and the approve had `id`, `result: "approved"`, `status: "done"`, `gates` and `item`, so both match. But a later change could break either unseen, and it's the shape an agent reads. Fix: run [review.rs:384](../../tests/review.rs#L384)'s and [review.rs:444](../../tests/review.rs#L444)'s approve through `Env::in_terminal_typing_sh` with `--json` and stdout redirected to a file, then check each against its schema.

## Slice 10 must decide

- **TR-6 is tracked by this slice's binary, so T6 and T9 can hold it.** All five of its criteria are manual as created, and the workflow gives each a check before `start`. If one is left manual, or it gets the `needs-review` label, the submit is held, the agent stops, and only the user at a terminal moves it on. Its own changes can't hold it, since this binary has no T1 to T8.
- **If TR-6 is held, its tree has to stay clean until it's approved.** `approve` re-runs G5 under `tracker/`, and G4's full `cargo test`. An uncommitted file there, such as a review being written, makes `approve` exit 2. Everything committed after the held submit, such as PLAN.md's "in review" and the readme, becomes part of the approved commit (design 1).
- **Whether `approve` runs the triggers.** Design 1: once T1 to T8 read commits, `approve` either runs them at the `HEAD` it names, or §2.7 and §7 say why not.
- **The triggers and `holds` in `gates`** (design 2), which slice 10's six triggers make more useful.
- **`review.disabled` must never switch off T6**, and T9 can be. `holds`' `{trigger, message}` shape has to stay as fixture XX-20 and the schemas have it, or gain a field with a serde default, when `show --diff` lists the files that fired a trigger first.
- **T4 and `c660f3b`.** Slice 10's T4 fires for an existing test with lines changed after `start`, as process 2 describes. If TR-5 is ever reopened and resubmitted, T4 holds it for `c660f3b`.
