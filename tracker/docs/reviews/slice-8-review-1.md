## Bugs

1. **A submit whose item file can't be written leaves a ref that `delete` never removes.** The submit arm sets the ref at [main.rs:2206](../../src/main.rs#L2206), under the lock, before the item is written, so a failed write leaves `refs/tracker/<ID>` for an item that isn't done. The readme says "The next verification moves it, and `delete` removes it" ([slice-8-readme.md:565](../slice-8-readme.md#L565)). But [`ref_to_delete`](../../src/main.rs#L2722-L2735) asks git only when the item's `verification` or `previous_verification` names a ref, and this item's records don't, so a delete leaves it.

   Reproduced: with `items/` made read-only, `submit XX-1` exited 3 with "Can't write …/XX-1.json.…tmp: Permission denied", the item stayed in progress, and `refs/tracker/XX-1` pointed at its commit. After `chmod 755`, a shelve and a delete typed under `script`, the item was gone and the ref was still there.

   It's an unlikely edge case: the write has to fail between the ref and the rename. Setting the ref first is the right order, since the other way round leaves a done item with no ref. The cost is a commit kept alive by a ref no item names. Fix: **(a)** have `ref_to_delete` ask `git::ref_exists` whenever the root can be found, whatever the records say. A root that can't be found still gives `None`, so deleting an item whose root has gone still needs no git. **(b)** Only correct the readme's sentence. I'd pick (a): it's one condition taken out.

2. **`delete`'s warning says "no checks ran" for `unchecked` records that ran 8 and 11.** [main.rs:2749](../../src/main.rs#L2749) prints "done at <time>, unchecked: no checks ran" for every `unchecked` record. That was true of records from before slice 7, but the slice 7 binary wrote `unchecked` records with `verification.checks`: TR-1's has 8 and TR-4's has 11, which I read with `tracker show`. Slice 8 changed this function, for the ref and the `auto` wording, so it's the place to fix it. The readme leaves it for slice 16 ([slice-8-readme.md:595](../slice-8-readme.md#L595)).

   Found by reading the code and the records. It's likely to be seen only if the user deletes TR-1 or TR-4, and the harm is a false line in the one prompt that exists to say what's lost. Fix: **(a)** for an `unchecked` record with checks, say "done at <time>, unchecked: its checks passed, but no commit ties them to the work", and keep today's words for one without. **(b)** Leave it to slice 16, as the readme says. I'd pick (a): it's one more arm of a `match`.

## Security

1. **Work hidden from git with `--skip-worktree`, `--assume-unchanged` or `.git/info/exclude` passes G5.** [`git::uncommitted`](../../src/git.rs#L104-L142) asks `git status`, which doesn't report a tracked file marked skip-worktree or assume-unchanged, however it's changed, and treats a path in `.git/info/exclude` or the user's `core.excludesFile` as ignored. §2.4's G5 says only "files that `.gitignore` excludes don't count", and gives the reason: "an untracked test helper could change what a test does without appearing in it." A committed `.gitignore` line at least shows in the item's commits. These three leave no trace in any commit.

   Reproduced, in a subfolder project with a check `grep -q done a.txt`: after `echo done > a.txt`, `gates` refused for G5. After `git update-index --skip-worktree a.txt`, `git status --porcelain` printed nothing, `submit` exited 0, "Verified automatically", and `git show refs/tracker/XX-1:xx/a.txt` printed `a`, not `done`. Then a check `test -f helper.sh`, with `helper.sh` untracked and listed in `.git/info/exclude`: the submit auto-verified, and `helper.sh` isn't in the verified commit's tree.

   An agent that's doing its work honestly won't hit this, so it's unlikely by accident. But it's a one-line command that turns G5's guarantee off without a trace, for the same agent G5 is meant to check, and the done item's record says its proof matches a real commit. Fix: **(a)** in `g5`, also run `git ls-files -v -- .` in the root and fail for each file whose tag is lowercase (assume-unchanged) or `S` (skip-worktree) and that exists in the work tree, so a sparse checkout, whose skipped files aren't on disk, still passes. Then say in §2.4 and §7 that "ignored" means git's own ignore rules, which include `.git/info/exclude` and `core.excludesFile`, and no commit shows those. **(b)** Say all of it in §7 only. I'd pick (a): the flags are one cheap git call, and the exclude files are a limit worth stating rather than closing, since a user's global ignore is ordinary.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **Nothing protects `refs/tracker/<ID>`, and §7 doesn't say so.** §2.7 says the ref "keeps the verified commit, and so the tests exactly as they ran, for as long as the ref exists", and §7 lists that it isn't pushed. But anything that can run git can move or delete it, with `git update-ref`, or a cleanup script that prunes refs it doesn't know. Then the item's `verification.commit` still names the commit, and a `gc` can prune it, so the proof the record points to is gone without a word. Found by reading. It's unlikely by accident, and an agent covering its tracks has easier ways (§7's plain-text files). Fix: **(a)** add a line to §7, and have slice 16's `audit` report a done `auto` or `human` item whose ref is missing or doesn't point at its `commit`. **(b)** The §7 line only. I'd pick (a), since `audit` is where §7 already sends the other hand edits.
