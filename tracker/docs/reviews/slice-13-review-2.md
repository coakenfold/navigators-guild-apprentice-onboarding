## Bugs

1. **A reply with `is_error` true and no message still gives a message that ends in a colon.** TR-49 fixed the path where `claude`'s output isn't JSON. The `is_error` path at [tracker-judge.rs:185-192](../../src/bin/tracker-judge.rs#L185-L192) takes `result`, or `subtype` when `result` is empty, and formats `"claude: {}"` with whatever `first_line` gives. Reproduced: fake `claude` replies of `{"is_error":true,"result":""}`, `{"is_error":true,"result":"   "}` and `{"is_error":true}` each gave `claude: ` on stderr, the shape review 1's bug 2 found. Very unlikely, since the CLI's JSON always carries a `subtype`, and low harm: the G3 message gives the user nothing to go on. Fix: **(a)** when the line is empty, say `claude reported an error and said nothing`, with a test beside `an_error_reply_fails_in_one_line`. **(b)** Leave it, and list it in the readme's Still open. I'd pick (a), but not as an item of its own: do it with the next change to `tracker-judge`, such as escaping `</material>` (review 1, security 1, option (a)).

## Where the code and DESIGN.md disagree, or the design is unclear

1. **§2.3.1's "Pinned model" bullet still promises what TR-49's new sentence takes back.** The bullet says the check means "a changed default or a fallback model can't answer in its place. The model that answered is recorded" ([DESIGN.md:192](../DESIGN.md#L192)). TR-49 changed only that bullet's last sentence. The paragraph after step 4 now says the check "is that the model asked for is present in `modelUsage`, not that it wrote the answer", and that "the reply's `model` always equals the request's" ([DESIGN.md:230](../DESIGN.md#L230)). So, 38 lines apart, §2.3.1 says both that a fallback can't answer and that one can, if the asked-for model took part, and that what's recorded is the model that answered and the model asked for. TR-49's criterion 3 checks that the new sentence is there, which it is, and nothing checks the old one. Certain to read inconsistently, and low harm, since the paragraph after step 4 is the more exact one and matches the code. Fix: reword the bullet: "The judge checks that the model it asked for is among those the CLI reports in `modelUsage`, and fails otherwise, so a changed default or a fallback model can't answer in its place unless the one asked for took part as well. The model asked for is recorded." I'd fold it into TR-48, which is a change to §2.3.1 already, rather than an item of its own.

2. **§7's interrupt bullet lists the wrong commands for judges.** TR-49 made it say "This goes for every command that runs checks or judges: `start`, `gates`, `submit`, `criterion add` and `set` after start, and shelving an in-progress item" ([DESIGN.md:811](../DESIGN.md#L811)). In slice 13, judges run only through [`ask_judges`](../../src/main.rs#L2050-L2054), which `gates`, `submit` and `approve` call. `start` runs no judge yet, since `move_item`'s `start` branch runs only `gates::criterion_runs` ([main.rs:2420-2440](../../src/main.rs#L2420-L2440)), `criterion add --judge` and `criterion set --judge` validate the file and run nothing, and a shelve runs only G5 and G4. `approve` runs both checks and judges, and isn't in the list for either: that omission predates this slice, for checks. The readme's own [What's in this slice](../slice-13-readme.md#whats-in-this-slice) says it right: "Judges still run only at submit, `gates` and `approve`." Found by reading. Low harm, since `approve` is run by the user at a terminal, who is the one pressing Ctrl-C, and slice 14 makes `start` true. Fix: name `approve` in the list, and say which commands run judges: `gates`, `submit` and `approve`, and `start` from slice 14. I'd fold it into TR-10, whose DESIGN.md change fires T8 anyway.

## Process

1. **Once `tracker-judge` is installed, a test that adds a judge without the fake calls the real `claude`.** The harness's [`Env::std_cmd`](../../tests/common/mod.rs#L76-L83) sets `TRACKER_HOME`, `HOME` and the folder, and keeps the inherited `PATH`. The default `judge.command` is `tracker-judge` ([config.rs:47](../../src/config.rs#L47)), found on `PATH`, and here the real `claude` is on `PATH` too, from nvm. `tests/judges.rs` sets its fake as the command through [`install_fake`](../../tests/judges.rs#L90-L102), and `tests/tracker_judge.rs` puts its own fake `claude` first on `PATH`, so no test reaches the default today: the whole suite, run with a logging fake `tracker-judge` and fake `claude` first on `PATH`, called neither. But in a throwaway store, a judge criterion with no `judge.command` set, and `gates` on the open item, ran whatever `tracker-judge` came first on `PATH`. Until now that was nothing, and such a test failed at "not found". After the install it's the real `tracker-judge`, which calls the real `claude`. Whether that call is logged in, with `HOME` a temporary folder, depends on where the CLI keeps its login, which wasn't checked. Slice 14 runs every judge at `start`, so its tests add judges to items they start, and one that forgets `install_fake` makes a real, paid call from inside `cargo test`, or a test that passes or fails by machine, and breaks the rule that no test calls the real `claude`. Moderately likely in slice 14, and the harm is a cost and a flaky test, not a wrong pass. Fix: **(a)** in slice 14's test commit, have the harness put a folder first on `PATH` holding a `tracker-judge` and a `claude` that exit 1 with "a test reached the real judge command". **(b)** Have `tracker init` in the harness write a `judge.command` that fails, and have `tests/judges.rs` replace it. **(c)** Rely on review. I'd pick (a): it covers every test file and both names. It edits `tests/common/mod.rs`, an existing test file, so it fires T4 on TR-10, which is held for the user anyway (T1, T8).

## Slice 14 must decide

Review 1's points still stand: what a failed call counts as under T11, what a failed call at `start` means, signals at `start`, TR-47 and TR-48 first, and that `tracker-judge` is installed and checked before any TR item has a judge ([review 1](slice-13-review-1.md#slice-14-must-decide)). This round adds:

- **Whether a fail before `start` counts toward T11.** §2.4 says `gates` "runs the criterion and project checks for an item in any state, not only one in progress, so an agent can see its checks fail before `start`" ([DESIGN.md:311](../DESIGN.md#L311)), and that it records failed judge requests for T11. Reproduced: `gates` on an open item ran its judge. An agent following §5 commits a stub and sees its judge fail on it before `start`, which is the expected fail that §2.4 doesn't count at `start` ([DESIGN.md:297](../DESIGN.md#L297)). TR-10's criterion 4, "An unchanged failure that `gates` repeats counts once, and fails at start don't count", doesn't say whether a `gates` run after `start` that repeats a request first failed at `start` counts once or not at all. I'd count only fails while the item is in progress, and never a request fingerprint that first failed before or at `start`, since unchanged work failing the same way isn't a retry.
- **Where a failed call's fingerprint comes from, if it counts.** [`judge::grade`](../../src/judge.rs#L348-L359) records a failed call as a message in `Graded.failures`, a string with no request fingerprint, and only an answered question carries one, in `Answered.request` ([judge.rs:375](../../src/judge.rs#L375)). So counting answered fails only, as review 1 suggested, fits the code as it is, and counting failed calls needs a fingerprint added to the failure.
- **The test harness guard** (process 1), in TR-10's test commit, before the first test that starts an item with a judge.
- **§7's command list** (design 2), in TR-10's DESIGN.md change, with `start` now true and `approve` added.
- **Run judges at `start` outside the lock**, as `start` runs checks: `move_item` drops the lock before `gates::criterion_runs` and takes it again with `lock_unchanged_after_checks` ([main.rs:2420-2440](../../src/main.rs#L2420-L2440)). A judge can take `judge.timeout_secs` (60) for each question, and holding the lock that long would block every other `tracker` command.
