## Verdict

Slice 10 does what the plan asks. `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo clippy --all-targets -- -D warnings` and all 371 tests pass, the count and the per-file split the readme gives, with 33 in [tests/risky_changes.rs](../../tests/risky_changes.rs). Every _Done when_ bullet has a test, and each of TR-6's seven checks runs one module of that file, matching 17, 5, 3, 2, 1, 2 and 1 tests in the record's saved output. The readme's demo prints what the readme shows.

- **The triggers read git, not the agent, and get the folder rule right.** One `git show` with `--no-renames`, `--no-ext-diff`, `--no-textconv` and `-z` lists every item commit's files ([git.rs:305-356](../../src/git.rs#L305-L356)), in the order given, which I checked against commits with different dates. Paths are stripped of the root's prefix before any glob, files outside the root count only toward T7, and the globs are built with `literal_separator`, so `*` stops at `/`. `**/package.json` matches `judge-eval/package.json` as well as one at the root, which the readme lists as untested and I checked by hand.
- **No hold I could find fires wrongly or says the wrong thing in TR's normal use.** For TR's slice items, every hold this binary will place is accurate: T1 for `capability`, T7 because a slice's tests alone pass 300 lines, T8 for `docs/DESIGN.md`, T3 for `Cargo.toml` or `judge-eval/package.json`, and T4 for the pinned `triggers` lists each slice updates. The misleading texts are edge cases: bugs 2 and 3.
- **`approve` doesn't refuse what it should accept.** It runs the triggers before the question, at the `HEAD` the question names, keeps the holds it showed, and exits 1 only if `HEAD` moved between the question and the gates. `HEAD` is the whole repository's, so a commit anywhere in guild-portfolio during that window makes it exit 1, but nothing is written and running it again works. A config change between the submit and the approve can make its question wrong (bug 2), not its outcome.
- **TR-6 was tracked as the rules ask.** Its tests were committed at 00:37:48Z, 46 seconds before `tracker start`, all seven checks failed at start, every commit of its work is scoped to it, and the installed slice 9 binary verified it `auto` at `e650ecf` with `refs/tracker/TR-6`. As the readme says, this slice's own rules would have held it under T1, T3, T7 and T8. Nothing in TR-6's record needs a second look, but by the bootstrap rule this review is the human look.

The findings that matter most:

- **Design 1:** an item's own tests, committed before `start` as the workflow asks, can be weakened after `start` without firing T4. I reproduced it, and a test pins it. It's the likeliest way for work to slip past a trigger in TR's real use: every TR item writes its tests first, and builders are told to fix a test that turns out to be wrong. Fix it before this binary is installed, or slice 11's item is judged with the gap open.
- **Security 1:** `git config diff.relative true` in the repository, which no commit shows, silences T1, T2, T3, T4 and T8 for a project in a subfolder. A `-diff` attribute in `.git/info/attributes` hides lines from T7. Neither happens by accident here, and the first is a one-flag fix.
- **Design 2:** T4's hold doesn't say which commit changed a test, so the expected-value updates slice 11 must make before `start` look the same as an edit after it.
- **Bug 1:** a misspelled key in `review`, such as `risky_path`, is ignored without a word. It matters as soon as the user writes TR's `review` settings by hand.

## Bugs

1. **A misspelled key in a project's `review` settings is ignored without a word, so the trigger it was meant to tune runs on its default.** `Review` ([config.rs:47-67](../../src/config.rs#L47-L67)) has serde defaults and doesn't deny unknown fields, so `"risky_path": ["src/store.rs"]` leaves T2 switched off, since `risky_paths` defaults to empty, and `"max_diff_line": 50` leaves T7 at 300. Reproduced: with `{"risky_path": ["src/lib.rs"], "max_diff_line": 1}`, an item that changed `src/lib.rs` passed `gates` with no hold. A value of the wrong type is refused with exit 3, as it should be. The user hasn't written TR's `review` settings yet and will do it by hand, so this is the likeliest way a setting fails to take effect. It fails open, and nothing shows it but a hold that never comes. Fix: **(a)** put `#[serde(deny_unknown_fields)]` on `Review` and add a `digest` field, since §4.2's example has `review.digest`, so a misspelled key exits 3 naming it, as a bad glob does. **(b)** Warn about unknown keys and carry on. I'd pick (a): it matches the bad-glob rule, and §4.2 lists every key `review` takes.

2. **When a submit's hold no longer fires at `approve`, the question says the item has "no trigger recorded" and doesn't say what went away.** [decision_warning](../../src/main.rs#L3285-L3303) prints only the holds `approve` worked out at `HEAD` ([main.rs:3154](../../src/main.rs#L3154)). A hold from the submit that doesn't fire there isn't shown at all, and if none fires, the line reads ", with no trigger recorded." though `item.holds` recorded one. Reproduced under `script`: XX-1 was held by T3, then `"disabled": ["T3"]` went into its `review` settings, and `approve`'s question said `XX-1 "a" is in review, with no trigger recorded.` What I approve is still what's verified, so the outcome is right. But the inbox listed T3, so the question disagrees with it without saying why. It needs a config edit or rewritten item commits while the item waits, so it's unlikely. Fix: list each of `item.holds` that no longer fires, marked "(no longer fires at <HEAD>)", and word the empty case as "nothing holds it at <HEAD>". It's a few lines in `decision_warning`.

3. **T1 names source files that the item added and then renamed or deleted, as if they were new.** In [changes](../../src/triggers.rs#L54-L82), a path goes into `added` on `A` and stays there after a later `D`. Reproduced: an item added `src/tmp.rs`, then renamed it to `src/search.rs` and renamed the existing `src/lib.rs` to `src/core.rs`. T1 said "new source files: src/core.rs, src/search.rs and src/tmp.rs", though `src/tmp.rs` no longer exists. T1 would fire anyway, so the hold is right, only its list is off. A rename of an existing source file counting as new is what §2.5 says. It's unlikely in TR, where a slice seldom adds a file and then moves it. Fix: on `D` of a path in `added`, remove it from `added`, so T1 lists only files that exist at `HEAD`. A file added again later goes back in.

## Security

1. **Two git settings that no commit shows can hide changes from the file triggers.** Both were reproduced on a project in a subfolder, as TR is:
   - With `git config diff.relative true` in the repository, `git show` names files relative to the folder it runs in, and leaves out every file outside it. Every path then fails the strip of `xx/` ([triggers.rs:63-65](../../src/triggers.rs#L63-L65)), so T1, T2, T3, T4 and T8 never fire, and T7 counts only lines inside the root. An item that added `src/search.rs`, edited `tests/old.rs` and changed `DESIGN.md` was held by T1, T4 and T8, and passed with no hold once the setting was on. `show --diff` then also drops files outside the root, which §2.1 says it shows.
   - A `-diff` attribute, such as `*.rs -diff` in `.git/info/attributes`, makes numstat report a text file as binary, with no line counts, so T7 counts none of its lines. A 400-line change to `src/lib.rs` passed with no T7 hold. T4 still fires for a test file, since it treats any change to a binary one as a change, so that half fails safe. A committed `.gitattributes` does the same, but shows in the diff.

   Neither is set in the user's git config, and no honest tool sets them, so neither happens by accident. An agent would have to write `.git/config` or `.git/info/attributes` on purpose, and G5 doesn't look there. But the first switches off five triggers at once, and the fix is one flag. Fix: add `--no-relative` to [git::changes](../../src/git.rs#L309-L321) and to `git::patches`, with a test that sets `diff.relative` in the throwaway repo. For the attributes, `--text` doesn't help, since numstat still says binary: **(a)** state it in §7, beside "G5 trusts git's ignore rules", or **(b)** count T7's lines from a `--text --patch` run instead of numstat. I'd pick (a) for the attributes, since T4 already fails safe and T7 is about size, not proof.

2. **An unscoped commit before `start` can delete an existing test, so that the item's own commit adds it back weakened and T4 stays quiet.** "Existing" means no item commit added the file, and slice 11's T14 looks only at commits after `started.head`. Reproduced: `chore: tidy` removed `tests/old.rs`, `test(XX-1): tests` added it back with its assert gone, and after `start` the item auto-verified. It takes a deliberate two-step, and the unscoped commit is in history for the digest's reader to find, so it's unlikely. Fix: **(a)** state it in §7's "Changed files depend on commit messages". **(b)** Have T4 ask git whether a test file the item added was deleted by an earlier commit, which needs history beyond the item's commits that the triggers don't read now. I'd pick (a).

## Where the code and DESIGN.md disagree, or the design is unclear

1. **An item can weaken a test it added itself after `start` without firing T4, and that's now the design.** [changes](../../src/triggers.rs#L67) calls a file existing only if no item commit added it, and `e650ecf` wrote this into §2.5: "T4 ignores a test file the item's own test commit added, however later commits change it." But in TR's workflow every item's tests are added by its own `test(TR-n)` commit before `start`, so after `start` none of them is existing, and T4 can never fire for them. Reproduced: `test(XX-1)` added `tests/new.rs` with `assert_eq!(search(), 3)`, XX-1 started, and `feat(XX-1)` replaced the body with nothing. The submit auto-verified, with no hold. [risky_changes.rs:384](../../tests/risky_changes.rs#L384) pins this, with a weakening (`1 + 1` to `0 + 2`). The readme lists it in Still open as a missing §7 line.

   §2.5's reason for T4 is "Editing tests to make them pass is the classic way an agent games verification", and an item editing its own failing tests after `start` is the most common form of it here. Slice 9 review 1's "Slice 10 must decide" expected T4 to fire for "an existing test with lines changed after `start`". The brief tells builders to fix a test that's genuinely wrong, so this will happen in honest work too, which is when I want to see it. How likely it is to matter: high for occurrence, in some item of slices 11 to 16. TR's slice items are `capability`, so T1 holds them anyway, but no hold points at the test. A review-fix item of kind `fix` or `change` that adds no source file auto-verifies.

   Fix: **(a)** for commits made after `started.head`, count a test file as existing when it exists at `started.head`, so any line removed from a test file after `start` fires T4, whoever added it. The rule before `start` stays as it is, so an item's test commit is free to add files. It needs to know which item commits `started.head` reaches, which slice 11's T14 also needs. Change §2.5's sentence, and the test at line 384 in the fix item's own test commit. **(b)** Keep the rule and add the §7 line the readme proposes. I'd pick (a), as a fix item before slice 10's binary is installed, since that binary judges TR-7.

2. **T4's hold doesn't say which commit changed the test, so an expected-value update made before `start` reads the same as an edit after it.** [t4](../../src/triggers.rs#L251-L281) names only files, "existing test file modified: tests/review.rs". From slice 11, the brief has builders update the tests a change will break in the item's test commit, before `start`, and TR-7 must add T5, T13 and T14 to the six pinned `triggers` lists, where T9's line, such as [review.rs:210](../../tests/review.rs#L210), has no trailing comma and so changes. So T4 will hold TR-7 and most later slices for sanctioned edits, and the user has to search `show --diff` to tell them from a weakening. That's certain to come up, and costs time on every such hold. Fix: **(a)** name each file's commits by short SHA in the message, marking those after `start`, such as "tests/review.rs (b7ba4ee, before start)". **(b)** Leave it, since `show --diff` lists the commits. I'd pick (a), and it fits with design 1's (a), which reads the same boundary.

3. **T3's message doesn't name the dependency, as §2.5's and §3's examples do.** The examples show `package.json changed (new dependency: "fuse.js")`, and [t3](../../src/triggers.rs#L228-L247) says "dependency manifest changed: package.json", which is true for any change, a version bump or a removed dependency included. It's only text, and T3's files tell me where to look. Fix: **(a)** change the two examples to the message the code gives. **(b)** Parse each manifest kind to find added dependencies. I'd pick (a): parsing thirteen manifest formats is far beyond what the hold needs.

4. **T7 counts every commit's lines, summed, and §7 doesn't say what that costs.** §2.5 now states the rule, so it's not a deviation. An item that adds a large file and later removes it is counted for both, which only over-holds, and in TR T7 fires for every slice item anyway. The readme lists it in Still open. Fix: add one clause to §7, or leave it, since §2.5 says it. I'd leave it.
