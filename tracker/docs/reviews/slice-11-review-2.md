**TR-41's T14 rule, (a) wrong holds.** It reads only `started.head..HEAD`, so a commit scoped to an earlier slice's item, or to an earlier fix, made before `start` never counts: the TR-41 replay shows it. It holds wrongly only when a commit scoped to another TR item enters that range: a branch move or restack while an item is in progress or in review, which the agents' brief already forbids, or the next item's test commit made while the current item waits in review, which the rules allow (process 1). The orchestrator's unscoped `docs:` commits are held as before TR-41, no more: at `5548c3a` TR-41's replay names `ba5acf3` and `5548c3a` beside `f2c796b`, and the brief's rule keeps them out of range.

**(b) Dodges.** One is left, and it's as easy as the one TR-41 closed: a scope whose key names no project at all, such as `feat(TRACKER-1)` or the typo `fix(T-41)`, is read as another project's work, so it gets past T14 and every trigger that reads files (security 1). Reproduced on TR-41's replay with a new module, a `Cargo.toml` change and edits to `src/store.rs` and `src/gates.rs`: only the real T4 and T8 fired.

The findings that matter most:

- **Security 1:** a commit scoped to a key that isn't a project gets past T14, T1 to T4, T7 and T8. Low likelihood, high harm, and a few lines to close for TR, which has one project.
- **Process 1:** the next item's test commit, made while the current item waits in review, holds it under T14 at `approve`, and the rules allow that commit. Moderate likelihood overnight.
- **Bug 1:** T14's message says "which no item's scope covers" for a commit that another item's scope does cover.
- **Design 1:** §5's agent block, §6 and §7 still say work scoped to another item's ID gets past T14.

## Bugs

1. **T14's message says "which no item's scope covers" for a commit scoped to another item, which that item's scope does cover.** [`t14`](../../src/triggers.rs#L491-L509) words every hold the same way, and TR-41 added a kind of commit it doesn't fit. Reproduced: TR-41's replay at `f2c796b` gives "T14 an unscoped commit since start, which no item's scope covers: f2c796b "test(TR-42): …"", and the TR-7 control gives the same for `fix(TR-7): sibling`. Certain whenever the sibling rule fires, and harmless beyond reading: the user at `approve` is told something the header beside it contradicts, and may take it for a bug in the hold. Fix: say what's checked, such as "an unscoped commit since start, not scoped to TR-41: …", or name a sibling's commit as "scoped to another item". The slice 11 fixture's stored message ([XX-23.json:42](../../tests/fixtures/slice-11/XX-23.json#L42)) is a record of what slice 11 wrote and can stay as it is. If a test reads the new message, it goes in a new test, so T4 doesn't fire.

## Security

1. **A commit scoped to a key that isn't a project gets past T14 and every trigger that reads files.** [`is_scoped_header`](../../src/git.rs#L384-L399) checks only the scope's shape, and [`scoped_to_a_sibling`](../../src/git.rs#L403-L410) counts it against the item only when its key is the item's own, so every other well-shaped key is read as another project's work. TR is the only project in the store, so for TR every such commit is a dodge. Reproduced on TR-41's replay: on top of `9012097`, `feat(TRACKER-1): add a feature and a module` (a `[features]` table in `Cargo.toml`, a new `src/hidden.rs` and a line in `src/store.rs`) and `fix(T-41): typo'd key` (a line in `src/gates.rs`) gave only TR-41's own T4 and T8. T1, T3 and T14 stayed quiet, and T7, which sums only the item's commits, leaves their lines out. The same commit scoped `fix(TR-7)` fires T14. It's also what [`t14_tells_another_project_from_another_item`](../../tests/tampered_proof.rs#L411-L425) asserts: its `YY` isn't a registered project. The readme's Decisions says so and calls it the narrowed §7 limit, but §2.5's T14 row speaks of "another project's key", which a reader takes to mean a project. Accidental hits need a typo that keeps the shape, such as a dropped letter in the key, so it's unlikely, and on purpose it's as easy as the sibling dodge TR-41 closed. Low likelihood, high harm: the work skips T1 to T4, T7, T8 and T14 at once. Fix: **(a)** count a scope as another project's only when its key is a registered project other than the item's. `triggers::run` already has the config, so `unscoped` takes the other keys. For TR, every scope but the item's own then fires T14. Replace `t14_tells_another_project_from_another_item`'s `YY` with a registered project in a new test, leaving the old test as it is or marking the edit before `start` so T4's hold says so, and add one for an unregistered key. **(b)** Also require that project's root to contain this one or sit inside it, since only a nested root explains its commits touching this root. I'd pick (a): it's the plain fix for the case TR has, and (b) can follow if a second project is ever registered.

## Process

1. **The next item's test commit, made while the current item waits in review, holds that item under T14, and the rules allow it.** The brief and the user's `~/.claude/CLAUDE.md` say not to write the next item's tests "until the current one is submitted", and a held item has been submitted. G1 still refuses the next `start`, but the test commit is already in. At `approve`, which runs the triggers again, it fires T14 marked new. Reproduced: TR-41's replay at `f2c796b`, as if TR-42's test commit had come before TR-41's approve, adds "T14 … f2c796b "test(TR-42): …"" to T4 and T8. In this round it didn't happen, since `f2c796b` came 3 minutes after TR-41's approve, with the user awake. Overnight a held item waits for hours, and a fixer spawned for the next item will do exactly this. Before TR-41, that commit was ignored. It doesn't stop the approve, but it's one more hold to read, and after a reject every resubmit is held again, since the commit can't leave the range without a branch move. A restack while an item is in progress or in review now brings in other items' rewritten commits as holds too, which the brief's rule on branch moves already covers. Moderate likelihood, low harm. Fix: **(a)** extend the brief's T14 rule to scoped commits: no commit under `tracker/` scoped to another TR item, as for an unscoped one, while a TR item is in progress or in review, so the next item's tests wait until the current one is done. **(b)** Exempt commits scoped to an item that's still open, which reopens the dodge TR-41 closed, since an agent can scope its work to the next item. I'd pick (a).
