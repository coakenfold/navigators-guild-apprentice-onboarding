## Process

1. **TR-29 changed two existing tests after `start`, which review 1's process 2 advised against, though its Outcome says the builders now follow that advice.** `tracker start TR-29` ran at 23:38:30Z. `f4fd771`, the feat commit at 23:45:07Z, added `triggers` and `holds` to the exact JSON that `a_script_criterion_needs_no_evidence` pins ([gates.rs:429](../../tests/gates.rs#L429)), and to the gates sample in [tests/schemas.rs](../../tests/schemas.rs), with new bad cases. Both changes were foreseeable before `start`: one test compares the whole dry run's output, and the other has to satisfy the schema whose `required` list the fix extends. The readme is open about it ([slice-9-readme.md](../slice-9-readme.md#tracking-review-1s-fixes)). Unlike `c660f3b`, the tests changed in the same commit as the code, so no commit fails the suite, and nothing was weakened: only fields were added.

   The harm is small now, and it grows later. Slice 10's T4 fires for lines changed in an existing test file in any of an item's commits, before or after `start`. So moving the change into the test commit doesn't avoid the hold. It does mean the updated test is seen failing before `start` along with the new ones, which is what the rules ask. From slice 11 on, when slice 10's binary tracks the items, every fix that changes an output's shape will be held under T4 and need the user. Fix: **(a)** for review fixes, change the tests a fix foreseeably breaks in the item's test commit, so they're seen failing before `start`, and expect T4 to hold such an item from slice 11 on. **(b)** Leave it to each item. I'd pick (a). It costs nothing now, and it makes T4's holds about tests changed on purpose.

2. **TR-29's criterion 3 check passes when DESIGN.md can't be read.** The check is `! grep -qF '"triggers": []' docs/DESIGN.md`. `grep` exits 2 for a missing or unreadable file, and `!` turns that into 0. Reproduced: run in an empty folder, it printed "grep: docs/DESIGN.md: No such file or directory" and exited 0. This is unlikely: DESIGN.md is TR's design doc, and G6 fails the submit if it's missing. It matters only if TR-29 is reopened, or if this kind of check is copied for a file that can go away. Fix: **(a)** for a negative `grep` in later items, check that the file is there first, such as `test -f docs/DESIGN.md && ! grep -qF …`, or write a test. **(b)** No change. I'd pick (a) for new items, and leave TR-29's check as it is, since it's done and its criterion holds.

## Slice 10 must decide

- **TR-6's five criteria are all manual.** `tracker show TR-6` gives none of them a check. The workflow gives each one a check before `start`. Any criterion left manual, or added later without a check, holds TR-6 under T6, and since TR-29 the agent sees that in `gates` once every gate passes. If TR-6 is held, its project is paused until the user decides it, which blocks TR-7's `start`.
- **If TR-6 is held, keep the tree under `tracker/` clean until it's approved, and wait to mark the slice `in review`.** `approve` re-runs G5 and G4, and the run above took 67 seconds for G4. An uncommitted readme or review makes it exit 2. PLAN.md's Status column says a slice becomes `in review` when its item reaches done, which for a held item is the approve, not the submit. A commit made while the item waits, like `4c19e71` made 4 seconds after TR-5's submit, becomes part of the approved commit (review 1's design 1).
- **From slice 11 on, slice 10's binary will hold nearly every TR item.** TR-7 to TR-12 are all `capability`, so T1 holds each one. Slice items usually change DESIGN.md, as `10e519a` and `fae0005` did, which fires T8. Fixes that change a pinned test fire T4 (process 1). §2.5 lets a project switch off T1, T4 and T8, but not T6. Slice 10 should decide whether TR's `review` config switches any of them off, or accept that the user approves every slice item from slice 11 on. Slice 11's T13 adds test-only fixes like TR-30, whose checks pass at start.
- **Design 1:** whether `approve` runs the triggers at the `HEAD` it names, once T1 to T8 read commits. `gates_dry_run` already calls `triggers::run` ([main.rs:1842](../../src/main.rs#L1842)), so it needs the same inputs as `submit`'s call when the new triggers read git and the config.
- **`review.disabled` must never switch off T6**, and `holds`' `{trigger, message}` shape has to stay loadable for fixture XX-20 when `show --diff` lists the files that fired a trigger first.
