## Verdict

Slice 12 does what the plan asks. Judge criteria are added and replaced with `--judge`, validated, graded once every other gate has passed, cached by request fingerprint, and recorded per question, and an unsure answer or `auto_verify: false` holds the item under T10, which can't be switched off. `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo clippy --all-targets -- -D warnings` and all 451 tests pass, the count and split the readme gives, 36 more than slice 11: 32 in [tests/judges.rs](../../tests/judges.rs), 3 unit tests in `src/judge.rs` and 1 in [tests/fixtures.rs](../../tests/fixtures.rs). TR-8 was tracked as the rules ask: `b8f378c` was committed 21 seconds before `start`, all ten checks failed at `start`, each check's saved output names the tests its `criterion_n::` filter meant (3, 2, 4, 1, 2, 8, 3, 4, 2 and 3, 32 in all), and the nine written criteria are unchanged. It was held under T1, T3, T4, T7 and T8, and approved by the user from a terminal, `human` at `932c1c4`.

It gets the parts later slices lean on right: the request is the shape judge-eval's adapter reads (`state` keeps its order, since serde_json's `preserve_order` is on), refs are `c<n>:<file>:<line>:<id>`, judge fields serialize only when set, so slice 11's XX-23 fingerprint test passes unchanged, a judge's answers stay out of the criterion T5 hashes, every reason and excerpt is escaped on output, and the real store loads unchanged. For TR's own script-only items, nothing changes but a quiet T10 in `triggers`.

The findings that matter most:

- **Design 2:** an unsure answer is shown only as its ref and reason, never with its question or excerpt, so the user decides a T10 hold without seeing what the model saw. Every T10 hold, and nothing stores the excerpt.
- **Security 1:** a judge answer forged once, by a `tracker-judge` on the agent's `PATH` or a file written into `judge/cache/`, is reused by every later run, the user's `approve` included. Deliberate only, but nothing shows it happened.
- **Design 1:** §2.3.1's step 4 still says the `adapter` field goes into the cache key, which the bullet this slice rewrote says it can't. Slice 13 builds `tracker-judge` from those steps.
- **Bug 1:** `approve` asks the judges before it checks for a terminal, so a piped `tracker approve` calls the judge, and before the script gates.
- **Bug 2:** in a `diff` input, a `\ No newline at end of file` line ends comment stripping for the rest of that hunk. The `diff` path has no test (test gap 1).

What was done about each finding, after the review, is under [Outcome](#outcome) at the end.

## Bugs

1. **`approve` asks the judges before it checks for a terminal, and before the script gates.** [`approve`](../../src/main.rs#L3391-L3396) runs `ask_judges` on an empty report, to give T10's reasons to the question, and only then calls `tty::confirm`, whose first step is `require_interactive`. So a piped `tracker approve` calls the judge command for any answer that isn't cached, and then refuses. Reproduced: an item held under T10, its cache folder removed, then `echo XX-1 | tracker approve XX-1` printed "Asking criterion 1's judge 1 question" before "needs a human at an interactive terminal", and the fake judge's call count went from 1 to 2. The readme's Still open names the second half: a check that would fail doesn't stop that first call either. With unchanged work and an intact cache, every answer comes from the cache, so today it costs nothing. Once slice 13's `tracker-judge` is the command, an agent that runs `approve` by mistake spends real calls, and waits up to `timeout_secs` for each question and excerpt, on a command that was never going to run. Low likelihood, low harm. Fix: **(a)** call `tty::require_interactive` at the top of `approve`, before the triggers run, so a refused approve does nothing. **(b)** Also make the first pass read only the cache, which a miss can only mean the cache was cleared or the config changed, since `approve` already refuses a moved `HEAD`. I'd pick (a): it's a line, and (b) adds a second way to grade.

2. **In a `diff` input, a `\ No newline at end of file` line ends comment stripping for the rest of its hunk.** [`strip_diff`](../../src/judge.rs#L844-L857) treats only lines starting with `+`, `-` or space as part of a hunk, and sets `in_hunk` from whether a line starts with `@@`. git prints `\ No newline at end of file` inside a hunk, after the last line of either side, so when a change touches a file's last line, the `+` lines after the old side's marker are passed through unstripped. Reproduced: an item commit that changed `fn b() {  }` at the end of a file without a final newline sent the judge `+fn b() { /* trust me */ }` and `+fn c() {} // still fine`, while the earlier commit's comments were stripped. Only a file with no final newline, changed at its end, so low likelihood. rustfmt adds the newline, but JSON, shell and many editors' files lack it. The harm is the one stripping exists to stop: an arguing comment reaches the model (§2.3.1, §7). The `diff` path has no test (test gap 1). Fix: keep a `\` line inside the hunk as it is, without feeding it to `strip_comments` and without ending the hunk. The same scanner reads every `#` outside a string as a comment in the hash style, so a shell `$#` or `${#arr[@]}` loses its tail in the excerpt. That one changes what the judge sees of the code, not which comments it sees, and can wait.

3. **`criterion set --judge` after `start` keeps the old check's `started.checks` entry, so T13 can blame a check the criterion no longer has.** `criterion set --check` after `start` runs the new check and replaces criterion n's entry ([main.rs:1658](../../src/main.rs#L1658)), but [`criterion_judge`](../../src/main.rs#L1752) only swaps the criterion. Reproduced: a criterion with the check `true`, which passed at `start`, then `criterion set XX-1 1 --judge …`, then a submit, held under T5 and "T13 criterion 1's check already passed before the work, so it can't be proving it", for a criterion that's now a judge. T5 fires for the change anyway, so the item is held either way, and the message is only misleading. The other case matters for slice 14: a judge that replaced a check that failed at `start` keeps `passed: false`, which slice 14's T13 for judges must not read as the judge's own start result. Low harm today. Fix: drop criterion n's entry when `set --judge` replaces a criterion after `start`, so T13 reads it as missing, as it reads a check given in review (§2.4).

4. **A huge `context_lines` in a judge file panics, and a huge `judge.timeout_secs` panics as `check_timeout_secs` already does.** [`excerpts`](../../src/judge.rs#L481-L482) adds `context` to the line number unchecked, and [`grade`](../../src/judge.rs#L342) multiplies the timeout by the question count. Reproduced: `"context_lines": 18446744073709551615` passes `criterion add --judge` (whose own check runs with a context of 0), then `gates` panics with "attempt to add with overflow" at `src/judge.rs:482` in the debug build. A release build, which `cargo install` makes, wraps instead, so `last` falls below the match and the excerpt silently loses the matched line. `"timeout_secs": 18446744073709551615` with two questions panics with "overflow when multiplying duration by scalar", and `check_timeout_secs` set the same way already panics in `checks.rs:142`, from slice 7. Only a hand-written absurd value, so unlikely, and §4.4 says a command never panics. Fix: `saturating_add` in `excerpts` and `saturating_mul` for the timeout, or refuse a `context_lines` above a few hundred in `parse_file`. `tracker create` an item for `check_timeout_secs`, which is outside this slice.

## Security

1. **A judge answer forged once, by a `tracker-judge` on the agent's `PATH` or a file written into `judge/cache/`, is reused by every later run, the user's `approve` included, and nothing shows it.** The judge command runs through `sh -c` in the caller's environment ([judge.rs:658-669](../../src/judge.rs#L658-L669)), and an agent's shell sets `tracker`'s `PATH`. The cache key is the command's text and the request ([`fingerprint`](../../src/judge.rs#L528-L534)), so it's the same whichever program that text found. Reproduced with the default command and no `tracker-judge` installed: `gates` failed G3 with "command not found". Then `PATH=<shim>:$PATH tracker gates XX-1`, where the shim prints a yes, passed. Then a plain `tracker submit XX-1`, with the shim gone, said "answered from the cache" and moved the item to done, `auto`. The fingerprint is a documented SHA-256 of JSON the agent can rebuild, so writing the cache file with `echo` does the same. A forged check is caught at `approve`, which runs `cargo test` again in my terminal, and a hand-edited item is caught by slice 16's `audit`, but a forged answer is read back from the cache by every later run, my `approve` included, and the record holds only the model and the fingerprint, which match. The cache keeps the adapter's name, so a shim that names another one shows only there. Deliberate only, so low likelihood, and high harm: it turns a judge into a pass with no trace in the item. §7's "The files are plain text" covers hand-edited items, not this. Fix: **(a)** put the judge program's resolved path in the fingerprint, from `command -v` of the command's first word, so an answer from a shim is never reused once `PATH` is normal again, and copy the reply's `adapter` into `verification.judges` so the digest can show it. **(b)** Say in §7 that the judge runs in the caller's environment and that the cache is trusted as written, so a forged entry passes unseen, like a hand-edited status that `audit` doesn't catch. I'd pick (b) now, and leave (a) to slice 13, which writes `tracker-judge` and may change the cache key anyway (the readme's Decisions).

## Where the code and DESIGN.md disagree, or the design is unclear

1. **§2.3.1's step 4 still says "The `adapter` field goes into the cache key", which the bullet `919e022` rewrote says can't be done.** [DESIGN.md:228](../DESIGN.md#L228) ends tracker-judge's reply step with that sentence, while [the "Cached by content" bullet](../DESIGN.md#L193) now says the key is the request and the command, with the adapter's name and version kept beside the answers, and the code agrees ([`fingerprint`](../../src/judge.rs#L528-L534)). Slice 13's prompt says to build `tracker-judge` "following §2.3.1's four steps", so it reads the stale one. Certain, and low harm, since the tool, not the adapter, computes the key. Fix: replace the sentence with "The tool keeps `adapter` beside the answers in its cache. It isn't part of the key (Cached by content)."

2. **An unsure answer is shown only as its ref and reason, never with its question or excerpt, though §2.3.1 says the gate output lists all four.** "When a question fails or is unsure, the gate output lists the question, the answer, the excerpt and the reason" ([DESIGN.md:195](../DESIGN.md#L195)). A fail gets them: [`refusal`](../../src/gates.rs#L216-L221) prints the excerpt under it. An unsure answer only reaches [`t10`](../../src/triggers.rs#L467-L495), whose hold message is "a judge answered unsure to c1:q, so a human decides: <reason>". Reproduced: for an item held under T10, `submit`, `gates`, `review` and `show` print just that line, and `gates --json`'s `judges` entry has the ref, answer and reason but no question or excerpt. Nothing stores the excerpt: the cache keeps the reply, not the request. So the user deciding a T10 hold, which exists so that "a human decides", can't see what the model was shown without rebuilding it by hand from the ref. Certain for every T10 hold, and moderate harm: overnight, every judge hold waits on a decision made blind. Fix: **(a)** have `gates` and `submit` print the question and excerpt under T10's hold, as under a G3 failure, and have `review`'s hint for a T10 hold name `tracker gates <ID>`, which answers from the cache and so shows the same excerpt again for free. **(b)** Store each unsure question's excerpt on the hold, so `review` and `show` print it, which slice 15's T12 needs anyway ("showing the excerpt, the model's answer and reason"). I'd pick (a) now and leave (b) to slice 15, which has to choose the stored shape for T12.

3. **`item::Question` refuses unknown fields, so a question field from a newer tracker makes the whole item unreadable, not refused as a newer file.** [`Question`](../../src/item.rs#L117-L118) has `deny_unknown_fields`, which the judge file needs, and the item file reuses the struct. Reproduced: a `weight` added to a question made `list` skip XX-1 as a file to "fix it by hand", `show XX-1` exit 3, and `start XX-2` fail G1 because "XX-1 … can't be read as an item". The same kind of field added at the criterion level (`rubric`) is listed and shown, and a write is refused as a newer tracker's, as CLAUDE.md's convention and §4.4 want. It needs a later slice to add a question field and an older binary to read the file, so it's unlikely in the bootstrap, where the installed binary writes TR's items, but the advice it gives is wrong. Fix: give the judge file its own question struct with `deny_unknown_fields`, so a typo such as `pass-when` in a judge file is still refused (dropping it would silently flip a defect question to pass on yes), and drop it from `item::Question`, so `lost_on_rewrite` and `refuse_newer_file` handle it as they handle the criterion.

4. **§2.3.1 doesn't say what `each` does over a `diff` input, or that commit subjects reach the judge.** A `diff` input is the item's patches as `git show` prints them, so its `each` lines are numbered in that concatenation, refs read `c2:diff:57:id`, and every new item commit renumbers them. Each commit's subject is in the excerpt too, and isn't stripped (bodies are left out, which was checked). Found by reading the code and the `diff` request reproduced for bug 2. Low harm: a dispute names the refs of the submit it's filed with, and §2.3.1 says "headers kept". Fix: one sentence in §2.3.1's comment bullet: for `diff`, `each` matches the patch text, lines count from its start, and commit subjects are kept, since an agent writes them.

2. **Nothing tests `approve` for an item with a judge**, neither the piped refusal nor a terminal approve of a T10 hold. This review approved one by hand in a pty in a throwaway store: it went to done, `human`, with the unsure answer in `verification.judges` and T10 in `verification.triggers`. A terminal approve stays a by-hand check, as PLAN.md's assumptions say.

3. **The tool's own model check and a judge command's non-zero exit are untested.** [`ask`](../../src/judge.rs#L613-L638) refuses both, and the readme and §2.3.1 promise it, but `criterion_3` covers only bad JSON, a bad answer and a missing question. judge-eval's adapter replies with the model it was asked for once `modelUsage` includes it, so for that adapter the tool's comparison is a second guard, and for a fake or another adapter it's the only one. Fix: two tests in a new module, a reply naming another model and a fake that exits 1 with a message on stderr, each failing G3 with that message.

## Slice 13 must decide

- **The cache key and the adapter's version.** Design 1's stale sentence, and security 1's (a): whether the resolved program, or `tracker-judge`'s version, goes into the fingerprint, so a new adapter, or a shim, doesn't reuse old answers. Today a fixed `tracker-judge` reuses slice 12's cached answers until `judge/cache/` is cleared, and on the real store there are none yet.
- **Which model the reply names.** The tool compares the reply's `model` with the one it asked for. `tracker-judge` should name a model it read from `modelUsage`, not echo the request's, as judge-eval's adapter does after its own check, or the tool's comparison proves nothing.
- **The request it reads.** `model`, `state` (an input's name, `diff` for the patches, or `match` and `code`) and `questions` keyed by id with `instructions` and optional `criteria.true` and `criteria.false`, in the order sent. It runs in the system's temporary folder, with `judge.timeout_secs` for each question, and its stderr becomes the G3 message on a failure.
- **Until it's installed**, slice 12's binary fails every judge with "command not found" for TR, whose config names no `judge.command`. TR's items are script-only, so nothing is blocked, but TR-9 shouldn't be given a judge criterion before `tracker-judge` is on `PATH`.
- **Bug 1 with a real judge.** If `approve`'s first pass isn't fixed first, every piped approve can cost real calls.

For slice 14, which runs judges at `start`: bug 3's stale `started.checks` entry must not be read as a judge's start result, so judges need their own start record, as the readme says. A `diff` judge's request holds each commit's SHA, so an amend makes a new fingerprint: T11 counts it as a new failure, which is right, and also gets a fresh answer, which T11 is there to limit.
