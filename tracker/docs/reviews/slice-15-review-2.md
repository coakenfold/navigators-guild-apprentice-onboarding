## Verdict

Slice 15 still does what PLAN.md asks, and TR-53's fixes are right. `count_failures` now runs as soon as the lock is taken again, before `check_disputes` ([main.rs:2556-2569](../../src/main.rs#L2556-L2569)), so a refused dispute counts its run as a `gates` run does. Review 1's security 1 is closed: replaying its attack, three versions each refused with `--dispute c1:works --dispute c9:nope` counted 1, 2 and 3 runs, and the plain submit of the fourth, passing version was held under T11 with "c1:works (3 runs)" instead of being auto-verified. A G3 failure with no answer skips `check_disputes`, so a failed call refuses with exit 2 and counts nothing, as before. Every held question carries `ask` ([item.rs:254-257](../../src/item.rs#L254-L257)), with a serde default and left out when empty, so slice 15's fixtures still come back byte for byte. Under `auto_verify: false`, `t10_questions` records every answer a judge didn't fail ([main.rs:2762-2782](../../src/main.rs#L2762-L2782)), and `approve` now records the submit's questions, as `reject` does. §2.3.2, the T11 row, §3, §4.3 and `submit.schema.json` say all of this. TR-53 was tracked as the rules ask: `109b32f` was committed at 18:39:50Z, 15 seconds before `start`, all 6 checks failed then, every commit since is scoped to TR-53, and the user approved its T4, T7 and T8 holds from a terminal, `human` at `7e32521`. `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` pass, and all **534 tests pass**, the count and split the readme gives.

Nothing here blocks the install. TR-12 has no judge criterion, so none of this slice's paths run for it, and its item file keeps slice 14's shape. What matters most is for slice 16:

- **Design 1:** now that `auto_verify: false` records a passing answer as a held question, an `approve` in one entry means I sided with the judge and in another that I overruled it. §2.3.2 and §3 say only that `judges` counts approves and rejects "for each judge question", and §6 calls them "agreement rates". TR-12's criterion 6 needs that settled before its test is written.
- **Design 2:** `approve` records only the submit's questions, so a T10 hold that appeared while the item waited, which `approve` shows as new and puts in `verification.triggers`, gets no decision recorded. Reproduced, and unlikely.
- **Bug 1:** a refused dispute says "Nothing was changed." though it has just counted a run toward T11. Reproduced.

## Bugs

1. **A refused dispute says "Nothing was changed." though it has just counted a run toward T11.** `check_disputes` ends every refusal with "Only a judge's fail can be disputed. Nothing was changed." ([main.rs:2730-2733](../../src/main.rs#L2730-L2733)), and since TR-53 it runs after `count_failures` has written `judge/failures.json` ([main.rs:2560](../../src/main.rs#L2560)). Reproduced: three refused `submit --dispute c1:works --reason x --dispute c9:nope --reason y` runs, on three versions that each failed `works`, all printed "… no judge question c9:nope was asked. … Nothing was changed.", while the count went 1, 2, 3, and the next submit was held under T11. The item file is unchanged, so the words are true of the item, but an agent reads them as a free try, which is what security 1's fix exists to stop it thinking. `Report::refusal`'s "can't be submitted: … Nothing was changed." ([gates.rs:179-181](../../src/gates.rs#L179-L181)) has said the same after a counted G3 fail since slice 14. Likely to be seen by any agent that hits a refusal on a judged item, and low harm: the T11 hold still comes, it just comes as a surprise. Fix: **(a)** say what counted: "BM-1 wasn't changed, but this run counted toward T11 (2 of 3)", in both refusals, which needs `count_failures` to say whether it added a run. **(b)** Say "BM-1 wasn't changed." in both, so nothing claims the try was free, and leave T11's count to the hold. I'd pick (b): it's one line each, and a count in the message would tell an agent exactly how many tries it has left.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **An `approve` of a held question now means opposite things in different entries, and DESIGN.md doesn't say how `judges` tells them apart.** Since TR-53, an `auto_verify: false` hold records each passing answer as `{"trigger": "T10", "answer": "yes", …}` ([main.rs:2773-2779](../../src/main.rs#L2773-L2779)), beside a disputed fail's `{"trigger": "T12", "answer": "no", …}` and an unsure answer's T10 entry. Approving the first sides with the judge, approving the second overrules it, and approving the third settles a question the judge left open. §2.3.2 says `judges` reports "for each judge question, how often I approved and how often I rejected the items it held", shown separately "rather than combined into one agreement rate" ([DESIGN.md:274](../DESIGN.md#L274)), and §3's row says the same ([DESIGN.md:455](../DESIGN.md#L455)). §6, though, has `judges` catching vague questions through "agreement rates" and showing "how often I side with the judge" ([DESIGN.md:789](../DESIGN.md#L789), [DESIGN.md:795](../DESIGN.md#L795)), which neither raw count gives. In a project with `auto_verify: false`, nearly every entry is a passing answer, so a question I keep overruling on disputes would still show mostly approves. A reject is noisier still: rejecting an item for a big diff records a reject against every passing question it held, which §2.3.2 warns of for one reject, but not for every reject of every judged item. Found by reading, from what `tr53_c3_approve_records_the_submits_t10_questions` records. Certain to matter once slice 16 counts, and harmless until then, since nothing reads the entries yet. Fix: **(a)** say in §2.3.2 and §3 that `judges` splits each question's approves and rejects by what held it: a disputed fail (T12), an unsure answer, and a passing answer held by `auto_verify: false`, which the entry's `trigger` and `answer` already tell apart, and make §6's two rows say "how often I approved a dispute of it". **(b)** Stop recording passing answers, which reverses review 1's design 2 option (b) and leaves an `auto_verify: false` project's decisions uncounted. I'd pick (a), settled before TR-12's criterion 6 test is written. No code changes in slice 15.

2. **`approve` records only the submit's held questions, so a T10 hold that appears while the item waits gets no decision recorded.** TR-53 took review 1's design 2 option (a): `approve` copies `item.held_questions` ([main.rs:3844-3847](../../src/main.rs#L3844-L3847)) instead of rebuilding them from its own re-ask. But `approve` still runs the triggers on its re-ask before asking ([main.rs:3777-3788](../../src/main.rs#L3777-L3788)), shows any new T10 hold, and records it in `verification.triggers`. Reproduced: BM-1 with two judge criteria, held under T12 for `c1:works`, then a scoped commit while it waited changed `src/other.rs`, the input of criterion 2, and the judge answered `c2:tidy` unsure. `approve` under `script` printed "T10 a judge answered unsure to c2:tidy … (new since the submit)", and after typing the ID the record had `verification.triggers` T1, T10 and T12, `verification.judges` with `c2:tidy` unsure, but `verification.held_questions` and the `approve` entry's `held_questions` held only `c1:works`. §2.7 says that when I approve an item a judge held under T10, the tool records my decision against each held question ([DESIGN.md:378](../DESIGN.md#L378)), and this one was held, and shown to me. Unlikely: it needs a commit while the item waits that changes a judged input to an unsure answer, and the decision is lost only from `judges`' counts. Fix: **(a)** have `approve` record the submit's questions plus each T10 question of its own re-ask whose ref and request aren't among them, so it records what it showed me, and `reject`, which asks no judge, keeps the submit's. **(b)** Say in §2.7 and §4.3 that a decision is recorded against the submit's held questions only. I'd pick (a), with a test in the shape of the reproduction.

3. **§2.3.2 says a failed judge call skips the dispute check, but the code skips it for any G3 failure with no answer.** `unasked` is any G3 failure whose `judge` is `None` ([main.rs:2563-2566](../../src/main.rs#L2563-L2566)), which covers a missing input, an `each` with no matches and an oversized excerpt as well as a failed call. §2.3.2 names only "a judge call fails and leaves no answer" ([DESIGN.md:256](../DESIGN.md#L256)). Reproduced: with `src/lib.rs` removed in a scoped commit, `submit BM-1 --dispute c9:nope --reason x` exited 2 for G3's "can't read its input", not 1 for the unasked ref. The behaviour is right, since each of these refuses the submit anyway, and it's only the wording that's narrower. Low. Fix: **(a)** say in §2.3.2 "or a judge leaves a question unanswered, such as when its call fails or its input is missing". **(b)** Leave it. I'd pick (a), with the next DESIGN.md change.

## Slice 16 must decide

- **What `judges` counts for a question** (design 1). Split each question's approves and rejects by what held it, using the entry's `trigger` and `answer`, and fix §6's "agreement rates". Settle it before TR-12's criterion 6, "`judges` shows the approve and reject counts for each question", gets its check.
- **Items, not entries.** An `each` question holds one entry per match, and under `auto_verify: false` every match of every question is an entry, so one `approve` can record the same `ask` many times. §2.3.2 counts "the items it held", so count each decision entry once per question.
- **The grouping key.** §4.3 says `judges` groups by `ask` within a project ([DESIGN.md:697](../DESIGN.md#L697)), and history entries don't carry the project, so read it from the item. An entry with no `ask` exists only in the two fixtures, since no binary before TR-53's code was ever installed with `held_questions`, so a plain fallback, such as the ref's question id marked as having no text, is enough.
- **Escaping `ask`.** It's text from a judge file the agent wrote, so `judges` and the digest must print it through `text::for_terminal`, as `disputed_text` prints the question ([main.rs:2818-2822](../../src/main.rs#L2818-L2822)).
- **Where decisions are read.** From every `approve` and `reject` history entry's `held_questions`, not from `verification`, which a reopen moves. A T11 hold records none, so `judges` should say its counts cover T10 and T12 holds only.
- **What the digest shows of a dispute.** An approved dispute, with the model's and the agent's reasons, is the line most worth a second look. A refused dispute now leaves its trace only as a counted run in `judge/failures.json`, which `start` empties, and in a T11 hold if it reaches one.
- **What `audit` checks of `held_questions`**, as review 1 said: present only while an item is in review, so one on an item in another state, a T12 hold with no T12 question, or the reverse, was written by hand.
- **The bootstrap.** Slice 15's binary tracks TR-12. TR-12 has no judge criterion, its item file keeps slice 14's shape, and none of its 7 criteria has a check yet, so each needs one, and its tests committed and seen failing, before `start`.
