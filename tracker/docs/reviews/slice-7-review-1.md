## Bugs

1. **A check that starts a process outside its group keeps `tracker` waiting past the timeout, until that process ends.** [`run`](../../src/checks.rs#L73) stops the group at the timeout, then joins the thread reading the output pipe at [checks.rs:128](../../src/checks.rs#L128). That read ends only when every process holding the pipe has closed it. A process that called `setsid` is in a group of its own, so `stop_group` misses it, and it still holds the pipe.

   Reproduced: with `check_timeout_secs` at 2, the check `python3 -c 'import os,time; os.setsid(); time.sleep(12)' & sleep 30` made `gates` take 12 seconds, not 2. It reported `timed_out: true`, but only once the escaped process ended. A process that never ends would hang `tracker` for good.

   The readme's limits say such a process "isn't stopped" ([slice-7-readme.md:451](../slice-7-readme.md#L451)), not that `tracker` then waits for it. It matters for test runners that start a server: Node's `spawn` with `detached: true`, for one, makes the child the leader of a new session on Unix, so a timed-out runner can leave such a server holding the pipe. Fix: **(a)** after the group is stopped, wait for the reader for a short time only, such as one second, by having it send what it read over an `mpsc` channel and using `recv_timeout`, then go on with what it has and say in the failure that something the check started kept running. **(b)** Only say in the readme's limits and §7 that `tracker` waits. I'd pick (a): the timeout is meant to bound how long a submit takes.

2. **Ctrl-C on `tracker` leaves the running check going.** `process_group(0)` at [checks.rs:99](../../src/checks.rs#L99) takes the check out of the terminal's foreground group, so the terminal's SIGINT goes to `tracker` alone. `tracker` has no handler, so it dies without stopping the check's group.

   Reproduced: I started `tracker gates BM-1` in a process group of its own, as a shell does, with the check `sleep 4; touch survived`, and sent SIGINT to that group after a second. `tracker` exited at once on the signal. `ps` still showed `sh -c sleep 4; touch survived` and its `sleep`, and `survived` appeared three seconds later.

   A check that writes, such as `cargo test`, may die of SIGPIPE when it next prints, but a quiet one runs on in the project root after I think it stopped, and can race the next command's checks there. A tool that stops `tracker` with a signal to its process group, as an agent's command timeout may, does the same. Fix: **(a)** catch SIGINT, SIGTERM and SIGHUP while a check runs and stop its group before exiting. The standard library can't, so it needs a crate such as `signal-hook`, which §8 doesn't list yet. **(b)** Say in the readme's limits and §7 that stopping `tracker` doesn't stop its check. I'd pick (a), since agents running long `cargo test` checks under a command timeout are the normal case here. Slice 10's T3 will hold the new dependency for my review, as it should.

3. **A very large `check_timeout_secs` panics.** [`run`](../../src/checks.rs#L124) adds the timeout to `Instant::now()` with `+`, which panics on overflow, and [`check_timeout`](../../src/config.rs#L54-L59) takes any `u64`.

   Reproduced: with `"check_timeout_secs": 18446744073709551615` in `config.json`, `start` and `gates` both printed "panicked at src/checks.rs:124:48: overflow when adding duration to instant" and exited 101. Values up to `10000000000000` worked. §4.4 asks that bad data gives a clear message and never panics, and `config.json` is edited by hand. Fix: use `began.checked_add(timeout)`, and treat `None` as no deadline.

4. **`criterion add` and `criterion set` run a check before refusing a newer tracker's file.** [`criterion_add`](../../src/main.rs#L1425) and [`criterion_set`](../../src/main.rs#L1536) load the item at [main.rs:1432](../../src/main.rs#L1432) and [main.rs:1542](../../src/main.rs#L1542), run the new check in `run_check_given_after_start`, and only `update_item` refuses the file at the end. `gates` ([main.rs:1770](../../src/main.rs#L1770)) and every move ([main.rs:2140](../../src/main.rs#L2140)) refuse before they run anything. Slice 6 review 2's bug 1 was the same thing for `criterion accept`.

   Reproduced: I added `"head": "abc1234"` to an in-progress item's `started`, as slice 8 will write it. `criterion add BM-1 y --check "touch ran-anyway"` printed `Running criterion 2's check`, created `ran-anyway`, and then exited 3 with "… has fields this version of tracker doesn't know …: started. … Nothing was written."

   Nothing is lost, but a shell command ran for a change that was then refused. This is exactly the case the bootstrap makes likely: once slice 8 adds `started.head`, an installed slice 7 binary will meet such files. Fix: call `refuse_newer_file(store, &id, &file)` right after the load in both, as `gates_dry_run` does.

5. **A kept line has no length limit, so one check can add hundreds of kilobytes to the item file.** `last_lines` ([checks.rs:180](../../src/checks.rs#L180)) keeps 20 lines of the last 64 to 128 KiB the reader held, however long each line is. `verification.checks` keeps them in the file, and a refusal prints them.

   Reproduced: a check that printed 300,000 NUL bytes with no line break, then passed, kept a 78,816-character `output`, and the item file grew to 474,074 bytes, since JSON writes each NUL as `\u0000`. Minified test output and progress bars are long lines too. Fix: cut each kept line at a fixed length, such as 500 characters, as a reason is limited, and mark the cut with `…`.
