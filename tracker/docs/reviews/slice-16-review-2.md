## Bugs

1. **A judge with `each` never shows its question in the digest.** An `each` judge's ref is `c<n>:<file>:<line>:<id>` ([judge.rs:524-527](../../src/judge.rs#L524-L527)). `asked` splits the ref at its first colon and looks for a question whose id is everything after it ([digest.rs:254](../../src/digest.rs#L254), [digest.rs:263-266](../../src/digest.rs#L263-L266)), so for `c1:src/lib.rs:1:works` it looks for a question with the id `src/lib.rs:1:works`, finds none, and leaves the answer without its question. Reproduced: an item whose only criterion is an `each` judge (`"each": "fn run"`), auto-verified on the fake's yes, gave `refs: ['c1:src/lib.rs:1:works']` and no `questions` in `digest --json`, and the text line `judge c1:src/lib.rs:1:works answered yes: "The fake says yes."`, with no "asked". Review 1's design 2 asked for the question because §6 counts on the digest to catch vague judge questions ([DESIGN.md:789](../DESIGN.md#L789)), and §2.3.1's own example of a judge is an `each` judge. [`tr55_c4_a_judge_passed_entry_prints_each_question_asked`](../../tests/digest.rs#L682-L693) uses a whole-input judge only, and the readme says each judge-passed item shows its question ([What's in this slice](../slice-16-readme.md#whats-in-this-slice)), while its Decisions entry describes only the `c<n>:<id>` form. Certain for every `each` judge. Low harm today: TR has no judge criterion, and the ref, answer and reason still show. Fix: take the criterion from before the first colon and the id from after the last, `judge.judge_ref.rsplit_once(':')`, since a question id can't hold a colon ([judge.rs:101-105](../../src/judge.rs#L101-L105)). Add a test in the shape of the reproduction, and correct the readme's Decisions line. [Process 1](#process) says how to track it.

## Security

1. **`review` names the last ack only beside an overdue digest, so an ack made under `script` doesn't show there at all.** Review 1's security 1 was fixed with option (a): §7 now says "`review` and the digest show the last ack's time, whether it came from a terminal, and its counts, so an ack I didn't make stands out" ([DESIGN.md:816](../DESIGN.md#L816)). But `review` builds `last_ack` into its text and JSON only for digests that `is_overdue` passes ([main.rs:3789-3806](../../src/main.rs#L3789-L3806), [main.rs:3827-3844](../../src/main.rs#L3827-L3844), [main.rs:3869](../../src/main.rs#L3869)), and an ack empties its digest, which is then never overdue. Reproduced: XX-1 auto-verified with `every_days` 0, `digest ack --project XX` under `script` typing `ack`, then `review` printed "Nothing needs you." and `review --json` was `{"held": [], "skipped": []}`. Only `tracker digest` named the ack: "XX's digest is empty: … since it was last acknowledged, at 2026-11-24T02:54:53Z, from a terminal, with 1 item and 0 actions." The next time `review` names it is when a new entry turns `every_days` old, a week later by default. And "from a terminal" can't tell an ack apart: `digest ack` records `tty::is_interactive()` ([main.rs:4202](../../src/main.rs#L4202)) only after `tty::confirm` has refused anything that isn't a terminal ([tty.rs:57-58](../../src/tty.rs#L57-L58)), so every recorded ack says "from a terminal", and only a hand edit can make it say otherwise, as [`tr55_c3_review_and_digest_show_the_last_ack`](../../tests/digest.rs#L638-L679) does. That test checks `review` only with an overdue digest, which is why this went unseen. Unlikely, since it needs a deliberate `script` ack, and the harm is the one review 1 named: the digest that would have shown other actions made that way is emptied, and the inbox doesn't mention it. Fix: **(a)** make §7 and the readme say what's true: `review` names the last ack only beside an overdue digest, `tracker digest` always names it, and the time and counts are what to check, since every recorded ack says "from a terminal". **(b)** Have `review` add one line for each project acknowledged within the last `every_days`, such as "XX's digest was acknowledged at …, with 1 item and 0 actions". **(c)** Keep every ack, review 1's security 1 option (b), which its Outcome left out. I'd pick (a): design 1's decision keeps the inbox quiet on purpose, (b) would put a line in it for a week after every real ack, and §7 already accepts that the terminal check is a convention.
