## Verdict

Slice 11 does what the plan asks. T5, T13 and T14 hold as PLAN.md and §2.5 describe, the fingerprint is taken at `start` over each criterion without its evidence, then the kind and the design, and T14 shares T4's range through `since_range`. `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo clippy --all-targets -- -D warnings` and all 403 tests pass, the count and split the readme gives, with 17 in [tests/tampered_proof.rs](../../tests/tampered_proof.rs). TR-7 was tracked as the rules ask: `e7406d8` committed at 21:16:50Z, `start` at 21:17:19Z with all five checks failing, each check's filter matching its module's tests (2, 3, 2, 5 and 1), and the user's `approve` from a terminal at `ce58426` under T1, T3, T4, T7 and T8.

- **No wrong hold on TR's items from T5 or T14.** Replayed with this binary, TR-7 at `ce58426` gets exactly the five holds the slice 10 binary gave it, and T5, T13 and T14 stay quiet. TR-38 gets only T8, and TR-37 T1 and T13. `edit --priority high --label replay` after TR-37's `start` left T5 quiet. Evidence is left out of the fingerprint, and a check given before `start` comes before the fingerprint is taken. In TR's history, none of the 15 items that have a `started.head` had an unscoped commit between it and the verification commit, so the orchestrator's unscoped docs commits, made between items, can't reach T14. The fingerprint is what the readme says: XX-23's `criteria_hash`, recomputed independently, matches.
- **T13 reads `started.checks` as §2.4 says,** and will hold about a third of TR's review fixes, rightly by the design but at a cost (process 1).
- **The harness's `BEFORE_THE_WORK_FAILS` is sound where TR runs,** macOS, including inside an agent's shell. It's the plainest way that keeps the existing tests working, and it needs `-ww` to be safe from a narrow `COLUMNS` on Linux (test gap 5). It's also a working recipe for getting past T13 (security 1).

The findings that matter most:

- **Process 1:** T13 holds every review fix with a "stays quiet" or "still loads" criterion, and every test-only fix. That's 4 of TR's 15 items tracked since slice 8, and each hold pauses TR until the user decides. It's settled by how the orchestrator writes criteria.
- **Security 2:** a commit scoped to another item's ID gets past T14 and every trigger that reads files, and a test asserts it. It hasn't happened in TR's history, but a review fix's agent sees the slice item's ID in its description.
- **Design 1:** `criterion accept` doesn't clear the user's own edit after `start`, though the plan's prompt, §2.5 and §2.7 say it does. It's happened once in TR, on TR-1.
- **Test gap 1:** nothing pins the fingerprint, so slice 12's change to `Criterion` could move it unseen.

## Security

1. **The harness's check is a working recipe for getting past T13, and agents work in the repo that holds it.** `BEFORE_THE_WORK_FAILS` ([tests/common/mod.rs:16-18](../../tests/common/mod.rs#L16-L18)) fails only when its parent `tracker` was started with `start`, `in-progress` or `criterion`, which is exactly when T13's record is taken. Reproduced: XX-1 with the check `! ps -o args= -p $PPID | grep -qw start` and no real work recorded `passed: false` at `start`, warned about nothing, and went to done, verified `auto`, with no trigger fired. §6 says T13 catches `true` and filters that match nothing, and §7's "Weak checks are the soft spot" covers a weak test written during the work, but neither names a check that tells `start` from `submit`. The command is saved in the verification record and shown by `show`, and slice 16's digest will list it, so it's visible to a reader. It needs intent, so it's unlikely. Fix: **(a)** add it to §7 beside the `script` recipe: a check can read how it was run, such as its parent's arguments, and fail only at `start`, and only the saved command shows it. **(b)** Refuse checks that mention `PPID` or `ps`, which is a list that never ends. I'd pick (a).

2. **A commit scoped to another item's ID gets past T14, and past every trigger that reads files, and a test asserts it.** `is_scoped_header` ([git.rs:384-399](../../src/git.rs#L384-L399)) counts any scope shaped like an ID as scoped, so work committed as `fix(TR-7): …` while TR-40 is in progress is in no item's changes and in no T14 hold. `commits_scoped_elsewhere::t14_doesnt_fire_for_a_commit_scoped_to_another_item` ([tampered_proof.rs:389-403](../../tests/tampered_proof.rs#L389-L403)) submits XX-1 with a `docs(XX-2)` commit and asserts it reaches done. §2.5 and §7 state the limit, so this is by design. With one item at a time per project, though, a commit since `start` that touches the root and is scoped to another ID of the same project has no honest source in TR: the orchestrator commits only between items, and a fix for a failing project check is scoped to the current item (§5). By the commit log, no TR scope has ever reappeared after another item's commits, so it hasn't happened, but a review fix's description names the slice's item, such as TR-7, which an agent could take for its own. Low to moderate likelihood, and the work then skips T1 to T4, T7 and T8 as well. Fix: **(a)** keep the §7 limit. **(b)** In T14, count a commit since `start` as unscoped when its scope is another ID in the item's own project, keeping other projects' IDs scoped for a root nested in another project's, and say so in §2.5's T14 row and §7. A few lines in `unscoped`, which then needs the item's ID. I'd pick (b).

## Where the code and DESIGN.md disagree, or the design is unclear

1. **`criterion accept` doesn't clear the user's own edit after `start`, though PLAN.md's prompt, §2.5 and §2.7 say it does.** The prompt says "`criterion accept` clears my own hand edits". §2.5's T5 row says that after I edit a criterion by hand, accept "records the new text so this doesn't fire", and §2.7 says the same. But accept only rewrites `written`, and the fingerprint is taken only by `start` ([main.rs:2303-2317](../../src/main.rs#L2303-L2317)), so the hash half still fires. The readme's Decisions and §4.3's new bullet choose this on purpose, since retaking the hash at an accept could hide an agent's change to a check or the kind. Reproduced: XX-1 started, its criterion was removed and re-added with new text, `criterion accept` under `script` said "Accepted XX-1's criteria", and the submit was held by "T5 the criteria, their checks, the kind or the design changed after start". The item then can't auto-verify until it's started again, so each resubmit after a reject needs an approve. It's happened once in TR: TR-1's history has a `criterion-accept` from a terminal between its `start` and its `submit`, 1 of the 33 items started. Low likelihood, and it errs towards holds. Fix: **(a)** keep the code, and make §2.5's T5 row and §2.7's accept bullet say what §4.3 says: accepting stops only the `written` half, so an edit after `start` holds the item until it's started again. **(b)** Retake the fingerprint at an accept, with the question saying whether the criteria, checks, kind or design changed since `start`. I'd pick (a), since (b) puts the user's attention on the one question where an agent's change could slip through.

## Test gaps

1. **Nothing pins the fingerprint, so a change to what it hashes would fire T5 on every in-progress item unseen.** PLAN.md's integration risk says the fingerprint must not change while an item is in progress. `fingerprint::start_records_the_criteria_fingerprint_before_head` ([tampered_proof.rs:437](../../tests/tampered_proof.rs#L437)) checks only that the hash is 64 hex characters before `head`, and the fixture test checks the file's shape and holds. A new `Criterion` field serialized when unset, a renamed key, or `json!` without `preserve_order` would all pass every test. Slice 12 adds judge fields to `Criterion`, so it's the likeliest slice to do it. XX-23's stored hash, `ed3c8e84…`, equals the SHA-256 of `{"criteria":[{"text":"search finds near misses","check":…}],"kind":"change","design":null}` as Python's `json.dumps` writes it, so the fixture is a ready golden value. Fix: assert `tracker::triggers::fingerprint(&item) == item.started.criteria_hash` for XX-23 in `tests/fixtures.rs`, and for a second fixture with evidence, a design and a capability.

2. **The commonest way T5 fires in real use isn't tested: a check changed or given after `start`.** `criterion set` or `criterion add` on an in-progress item runs the new check ([main.rs:1538-1565](../../src/main.rs#L1538-L1565)) and changes the criteria, so T5 should fire beside any T13. `edit --design` after `start` isn't tested either. Both are covered by the one hash comparison that `criterion_3` exercises through the kind, so a regression is unlikely, but these are what an agent does. Fix: two tests in `tests/tampered_proof.rs`, each held by T5 with "changed after start".

3. **Nothing runs `criterion accept`, or a check given while the item is in review.** The prompt names accept, and T13's "old entry" reading (a check given in review keeps the old check's result) has no test. Both need a terminal, and `script` gives one, as `tests/show_and_delete.rs` does for `delete`. Fix: one test that an accept after a hand edit clears the `written` half and leaves the hash half (design 1), and one that a check given in review leaves the old `started.checks` entry, so a resubmit is held by T5, and by T13 if the old check had passed.

4. **T14's rewritten commits, missing `started.head` and merge commits are untested.** The readme lists the first two. `--full-history` ([git.rs:420](../../src/git.rs#L420)) lists a merge that differs from a parent under the root, headed "Merge branch …", which T14 holds, and no test shows it. Agents in TR don't merge, so it's unlikely. Fix: one test with a `--no-ff` merge of a scoped branch, held by T14 and naming the merge.

5. **`BEFORE_THE_WORK_FAILS` is sound on macOS, but `ps`'s output width and availability can break it elsewhere, loudly.** `$PPID` is the `tracker` that runs the check, since `checks::run` spawns `sh -c` directly ([checks.rs:100-110](../../src/checks.rs#L100-L110)), and `grep -w` matches `start`, `status <id> in-progress` and the `criterion` commands, so the check fails at `start` and after it, and passes at `gates`, `submit` and `approve`. On macOS, `ps -o args=` piped prints the whole line even with `COLUMNS=40` (tried), and the suite passes inside this session's shell. By reading, not running: procps-ng's `ps` lets `COLUMNS` cut piped output, so an exported narrow `COLUMNS` could drop `start` from a long path; a Linux image without procps, or BusyBox's `ps`, has no `ps -o … -p`; and a checkout path with `start` or `criterion` as a word, such as `~/quick-start/`, makes every such check fail everywhere. Each makes dozens of tests fail, none passes wrongly, and TR runs on macOS, so it's unlikely. The plainer-looking alternative, failing while `$TRACKER_HOME/items/<id>.json` says `"status": "open"`, is portable but fails `gates` before `start`, which `a_script_criterion_needs_no_evidence` and `gates_says_when_the_item_isnt_ready_to_submit` in `tests/gates.rs` rely on, and passes for a check given after `start`, so it would mean editing existing tests, which fires T4. Fix: **(a)** keep `ps` and make it `ps -ww -o args= -p $PPID`, which lifts the width limit in both BSD and procps, and say in the comment that it needs a `ps` with `-p`. **(b)** Switch to the status check and update the four tests. I'd pick (a).

## Process

1. **T13 will hold about a third of TR's review fixes, and each hold pauses TR until the user decides.** Of the 15 TR items with a `started.head`, 4 had a check pass at `start`: TR-30 (all three, since it only adds tests for behaviour that works), and criterion 2 of TR-31 ("isn't held under T4"), TR-34 and TR-37 ("still loads"). With this binary each is held by T13. The replay of TR-37 gives "T13 criterion 2's check already passed before the work, so it can't be proving it" beside T1. §2.4 means this, since a check that passes before the work proves nothing new, and slice 12 to 16's items are `capability` and held by T1 anyway. But TR-31 and TR-34 are `fix` items that this binary would otherwise have let through, and overnight a held fix stops every later one. Certain to happen with the current way of writing criteria. Fix: **(a)** have the orchestrator write each criterion so its check runs at least one test that fails first, putting a "stays quiet" or "still loads" case in the same filter as the case that fires, as TR-7's `criterion_N::` modules do, and leave plain regressions to G4's full suite; give each review's test-only fixes a single item, so they cost one hold. **(b)** Accept the holds and order such items last. I'd pick (a).

2. **The orchestrator's unscoped commits are safe only by its ordering, and the readme is the only place that says so.** T14 can't fire for a commit made before `start` (`criterion_4::t14_doesnt_fire_for_an_unscoped_commit_before_start`), and in TR's history none of the 15 items had one in range. But the replay of TR-38 at slice 10's `7a31712` instead of its verification commit fires T14 for `54751b9` and `7a31712`, the readme and Outcome commits made after it, and the replay of TR-7 at `c327e25` fires it for this slice's readme. TR-8 to TR-12 will wait in review under T1, often overnight, which is when the orchestrator wants to write a readme or a review. A commit made then shows at `approve` as a T14 hold "new since the submit". It doesn't stop the approve, but it's one more hold for the user to read past, and a restack of the branches while an item is in progress or in review brings every rewritten docs commit into range. Moderate likelihood, low harm. Fix: put the rule from the readme's [Limits](../slice-11-readme.md#limits-and-what-later-slices-change) into the orchestrator's brief: no unscoped commit under `tracker/`, and no restack, while a TR item is in progress or in review, or scope the commit to that item.

3. **The readme's claims check out, apart from two details.** The test count and split, the seven commits, TR-7's holds and timings and its five failing start checks are as it says, and its Try it holds (T5, T13 and T14 on BM-1, T5 on IM-1, done for LM-1) are what the code gives. The Still open list is accurate and complete for the code. Two slips: the stale comment it puts on `Started` is on `written` (bug 1), and "It relies on `ps -o args= -p`, which macOS and Linux both have" holds for procps but not BusyBox, and leaves out `COLUMNS` (test gap 5). Fix: correct both sentences when the readme is next updated.

## Slice 12 must decide

- **Judge fields and the fingerprint.** Slice 12 adds judge questions and inputs to `Criterion`. They must serialize only when set, so the fingerprint of a criterion without them is unchanged, and test gap 1's golden test should land first, so the change can't move it unseen. A judge's answers mustn't go into the criterion the fingerprint hashes. Install the new binary only between items, as the integration risk says.
- **The pinned trigger lists.** Six tests now pin eleven triggers. Adding T10 changes them, so slice 12's test commit, before `start`, will fire T4 on TR-8, as `e7406d8` did on TR-7.
- **Judges and T13.** Slice 12 doesn't run judges at `start`, so a judge criterion has no `started.checks` entry and T13 reads it as not passed, which is right until slice 14. `BEFORE_THE_WORK_FAILS` must still fail for any new command that runs a check before the work.
- **TR-8 in review.** It's a `capability`, so T1 holds it, and while it waits no unscoped commit should touch `tracker/` (process 2).
- **A lost `started.head`.** Slice 10 review 2's bug 3 is still undecided, and T14 now meets it with T4: `gates`, `submit` and `approve` exit 3 with git's error.
