## Bugs

1. **A committed file under the root whose name isn't UTF-8 makes every G5 exit 3, since TR-21.** [`git::hidden`](../../src/git.rs#L150-L172) runs `git ls-files -v -z -- .`, which lists every tracked file under the root, and the `git` helper refuses output that isn't UTF-8 ([git.rs:49-55](../../src/git.rs#L49-L55)). Before TR-21, G5 read only `git status`, which lists a file only while it's dirty, so a clean file with such a name passed. Now `gates`, `submit` and an in-progress shelve all exit 3 until the file is renamed.

   Reproduced, with a constructed repository, since macOS's file system refuses a name that isn't UTF-8 ("Illegal byte sequence"): I added `xx/caf\xe9.txt` to the index and committed it, then marked it skip-worktree so that `git status --porcelain` printed nothing, as it would for that file checked out cleanly on Linux. `gates XX-1` exited 3: "`git ls-files -v -z -- .` in …/repo/xx printed something that isn't UTF-8."

   It's an unlikely edge case: it needs a Linux checkout of a repository with a Latin-1 or similar file name under the root, and it fails closed, with a message naming the command. `uncommitted` and `item_commits` already exit 3 the same way for such a file while it's dirty, or for such a commit message, but those pass once the file is committed. Fix: **(a)** have `hidden` read `ls-files`' bytes, keep only the entries whose tag is flagged before decoding, and name the path with `String::from_utf8_lossy`. That needs a variant of the `git` helper that returns bytes. **(b)** State it in §7 alongside the other limits of reading git. I'd pick (b) for now: it's the plain fix for a case macOS can't even produce, and (a) is worth doing only if a real project hits it.

## Security

1. **A flagged file that's been deleted passes G5, so a failing test can be hidden from the checks and still be in the verified commit.** [`git::hidden`](../../src/git.rs#L166) lists a flagged file only if it's on disk, for either flag. §2.4's G5 row says only that "a skipped file that isn't on disk, as in a sparse checkout, passes" ([DESIGN.md:286](../DESIGN.md#L286)), so the assume-unchanged half also disagrees with the design. `git status` doesn't report a deletion of a file marked either way, so G5's other check doesn't see it either.

   Reproduced, once for each flag, in a subfolder project whose project check runs every `tests/*.sh`: the work commit added `tests/edge.sh`, which exits 1, and `gates` refused for G4. After `git update-index --assume-unchanged tests/edge.sh` (or `--skip-worktree`) and `rm tests/edge.sh`, `git status --porcelain` printed nothing, `submit` exited 0, "Verified automatically", and `git show refs/tracker/XX-1:xx/tests/edge.sh` printed `exit 1  # the edge case still fails`. So the record says every check passed at a commit whose own tests fail.

   An agent working honestly never sets these flags, so it's unlikely by accident. It's the same deliberate, traceless dodge review 1's security 1 described, and it's arguably the more tempting form: an agent stuck on a failing test can make it vanish without a `git rm` that slice 10's T4 would hold. TR-21's test asserts the case as passing, since `g5_fails_for_a_file_marked_skip_worktree` ends by deleting the flagged file in an ordinary repository and calling `g5_passes` ([commits.rs:199-201](../../tests/commits.rs#L199-L201)). Fix: **(a)** list an assume-unchanged file whether or not it's on disk, and a skip-worktree file that isn't on disk only when `git config --bool core.sparseCheckout` isn't `true`, and say so in §2.4's G5 row. The end of that test is then wrong, not weakened: make its repository a sparse checkout before deleting the file, and add a case where a deleted file in an ordinary repository fails. **(b)** List every flagged file, on disk or not, and state in §7 that a sparse checkout under the root fails G5. **(c)** A §7 line only. I'd pick (a): it's one more git call, and a sparse checkout still works.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **A check that marks a file skip-worktree and changes it passes G5's second look, though §2.4 says a check that changes a file under the root fails G5.** §2.4's "Checks leave the tree as they found it" ([DESIGN.md:291](../DESIGN.md#L291)) says a check that "changed or added a file under the root, other than one git ignores … fails G5". [`tree_after_checks`](../../src/gates.rs#L370-L402) asks only `git::uncommitted` and `HEAD`, and `git status` doesn't see a change to a skip-worktree file. The readme states the gap ([slice-8-readme.md:382](../slice-8-readme.md#L382), [slice-8-readme.md:662](../slice-8-readme.md#L662)), and DESIGN.md doesn't.

   Reproduced, in a subfolder project: a criterion check `git update-index --skip-worktree a.txt && echo done > a.txt && grep -q done a.txt` (with the flag and file put back after `start`, which runs the check too). `submit` exited 0, "Verified automatically". Afterwards `git ls-files -v` showed `S a.txt`, the file held `done`, and the verified commit's `xx/a.txt` held `a`. A new item, XX-2, then failed `gates` under G5: "XX's root has files git is told not to look at, … skip-worktree xx/a.txt. Clear the flag …, then commit any change, scoped to XX-2".

   How likely: very unlikely. No honest check sets the flag, and a check that means to cheat doesn't need it: one that writes a tracked file, runs its test and restores the file passes both looks with no flag at all. The second look is there to catch files a check leaves by accident, not to stop a check that sets out to deceive. A check sets a flag by accident only if it runs a tool that manages a sparse checkout. The proof isn't weakened either: the check's command is in the record, and running it again at the verified commit does the same thing. The real cost is the one §2.4 names: the leftover fails the next item's G5, or a shelve, rather than this submit, and tells that item to commit a change scoped to itself. Fix: **(a)** give `Report` a `hidden` list, set by `g5` as it sets `uncommitted`, and have `tree_after_checks` call `git::hidden` again and fail G5 for each new entry, as it does for `uncommitted`. It's about ten lines, and slice 9's `approve` gets it through the same call. **(b)** Add a sentence to §2.4 saying the second look doesn't ask about the flags. I'd pick (a), since §2.4 already promises it.

2. **In a repository with `core.ignoreStat` set, G5 refuses every submit, and its advice can't be followed.** With `core.ignoreStat=true`, git marks each file assume-unchanged whenever it updates one in both the index and the work tree, so every committed file under the root is flagged. Reproduced: in such a repository, after `feat(XX-1): b`, `git ls-files -v` showed `h a.txt` and `h b.txt`, and `submit` was refused under G5 for "assume-unchanged xx/a.txt and assume-unchanged xx/b.txt", telling the agent to clear the flags. Git sets them again at the next commit. Refusing is right, since `git status` can't see changes in such a repository and so G5 can't either. But neither §2.4 nor §7 says so, and the message sends the agent round in a loop. It's very unlikely: the setting is for slow file systems, and the real repo doesn't have it (I checked, read-only). Fix: **(a)** a §7 sentence that G5 can't work with `core.ignoreStat` and refuses until it's off. **(b)** Also detect it in `g5` and give one failure saying so, in place of the file list. I'd pick (a).
