## Verdict

Slice 14 does what PLAN.md asks. G1 refuses a judge with nothing to grade, `diff` or file or `each` ([gates.rs:572-599](../../src/gates.rs#L572-L599), [judge.rs:184-228](../../src/judge.rs#L184-L228)). `start` grades every judge once, outside the lock, with G3's own loop and cache ([main.rs:2459-2474](../../src/main.rs#L2459-L2474)), records each in `started.checks`, and T13 holds one that passed. T11 counts failed requests in `judge/failures.json`, once per fingerprint, only while the item is in progress, never one asked at `start`, and never a failed call. Slice 13's review points were all taken: the harness guard on `PATH` is in the test commit, §7's command list is right, and a failed call neither counts nor refuses `start`. TR-10 was tracked as the rules ask: `3fa1f52` was committed 46 seconds before `start`, all six checks failed then, every commit since is scoped to TR-10, and the user approved T1, T4, T7 and T8 from a terminal, `human` at `fdaa0cb`. `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` pass, and all **494 tests pass**, the count and split the readme gives.

Nothing here blocks the install. TR-11 and TR-12 have no judge criteria, so T11 never fires for them and `failures.json` is never read for them, except by bug 1. What matters, before slice 15 builds on T11's count:

- **Design 1:** T11 counts requests, not attempts. One failed try at an `each` judge with three matches holds the item at the default `max_failures` of 3, and a line added above a failing match makes it a new request though its code didn't change. Reproduced.
- **Security 1:** re-rolls before `start` are free, so an agent can fish for a pass on the open item, start on a stub, then restore the passing code from the cache, and get past both T11 and T13. Reproduced.
- **Bug 1:** a damaged `judge/failures.json` refuses `start` for every item in every project, judge or not, after running its checks. Reproduced, and unlikely.
- **Bug 2:** after a failed call at `start`, the stub's own fail counts toward T11 at the next `gates`, which §2.5 says never happens. Reproduced, and unlikely.

TR-47, TR-48 and TR-50 are still open and deferred, as the readme says. TR-47 now reaches `start` too, since G1 makes a `diff` judge grade the item's first commit there.

## Bugs

1. **A damaged `judge/failures.json` refuses `start` for every item, judge or not.** `apply` calls `judge::record_start` on every `start` ([main.rs:2470-2474](../../src/main.rs#L2470-L2474)), and `record_start` reads the file before it looks at whether there's anything to record ([judge.rs:277-281](../../src/judge.rs#L277-L281)). Reproduced: with a `failures.json` of `{"XX-9": {"failed": [`, `start YY-1`, an item in another project with only a `--check false` criterion, ran its check, then exited 3 with `Can't parse …/judge/failures.json, line 1, column 21: EOF while parsing a list. It's JSON that tracker writes, counting failed judge requests for T11 (§4.1). Fix it by hand, or remove it, which starts every item's count again.`, and YY-1 stayed open. `gates` and `submit` aren't affected for such an item, since `failed_requests` skips an item with no judge ([main.rs:2076-2081](../../src/main.rs#L2076-L2081)) and `record_failures` returns before reading when nothing failed. The readme's "It writes nothing for an item with no judge that has no entry" is true, but it still reads. Unlikely, since only `tracker` writes the file, and the message says how to recover, but it stops every project's work, TR's included, for a file that has nothing to do with them. Fix: **(a)** call `record_start` only for an item with a judge criterion, as `failed_requests` already decides, with a test that a damaged file doesn't stop a judgeless `start`. **(b)** Have `record_start` return before reading when `answers` is empty, which leaves a stale entry for an item whose judges all failed at start. I'd pick (a).

2. **After a failed call at `start`, the stub's own fail counts toward T11, and T13 can't see the judge.** A failed call leaves no answer, so `record_start` gets no fingerprint for it and `at_start` is empty ([main.rs:2470-2474](../../src/main.rs#L2470-L2474)). Fix: **(a)** say it in §2.4 and §2.5: T11 never counts a request answered at `start`, and a judge that couldn't be graded then is outside T13 and counts from its first answer. **(b)** Give `Graded` the fingerprint of each failed call and put it in `at_start`, which fixes T11 but not T13, and doesn't cover the excerpts a failed call stops `grade` from asking ([judge.rs:507-517](../../src/judge.rs#L507-L517)). ## Security

1. **Re-rolls before `start` are free, so an agent can fish for a pass, start on a stub, and restore it.** `gates` on an open item asks the judges and caches every answer, but counts nothing ([main.rs:2067-2072](../../src/main.rs#L2067-L2072)), and `start` empties the count anyway ([judge.rs:277-292](../../src/judge.rs#L277-L292)). Reproduced, with `max_failures: 1`: on open XX-1, `test(XX-1): try 1` failed `gates`, `test(XX-1): try 2` passed it, then `test(XX-1): stub` put the stub back, `start` asked the judge about the stub (it failed, so no T13, and `at_start` holds 1, `failed` 0), and `feat(XX-1): the work`, restoring try 2, was submitted: "Criterion 1's judge: answered from the cache", then `XX-1: in-progress → done`, auto-verified, with T11 and T13 quiet. The same two tries after `start` hold it under T11. §6 says "T11 holds the item after repeated judge failures" ([DESIGN.md:787](../DESIGN.md#L787)), and §2.4 that a dry run "can't be used to try out rewordings for free" ([DESIGN.md:311](../DESIGN.md#L311)), and neither mentions the window before `start`. §6's vague-question row already admits that a stub written to fail gets a vague question past T13 ([DESIGN.md:782](../DESIGN.md#L782)), and this is the same move used against T11 too. It needs a deliberate three-step, and the tries are in the item's commits for `show --diff` and the digest to show, so it's unlikely, but the harm is a wrong pass that the item's record doesn't flag. Fix: **(a)** state it in §7, beside the other two-step limits it states rather than closes ([DESIGN.md:826](../DESIGN.md#L826)), and in §6's T11 row. **(b)** Count failed requests on an open item as well, and have `start` drop only those it asks again, so the stub's expected fail still never counts. That reverses slice 13 review 2's advice, which this slice took, and still lets a reopened item's `start` clear its count. I'd pick (a) now, and (b) only if the digest shows it happening.

2. **Removing `judge/failures.json` clears every item's T11 count, and its own error says to.** `FAILURES_FIX` tells whoever hits a parse error to "Fix it by hand, or remove it, which starts every item's count again" ([judge.rs:249-251](../../src/judge.rs#L249-L251)), and most commands are run by agents. An `rm` of the file, unlike a hand-edited status, leaves nothing for slice 16's `audit` to find. Found by reading. Unlikely, since the file is only damaged by hand or a disk fault, and it's the same class as §7's forged cache bullet ([DESIGN.md:805](../DESIGN.md#L805)). Fix: **(a)** add `failures.json` to that §7 bullet, and end the error with "or remove it, which clears every item's T11 count, so a human should decide". **(b)** Leave it. I'd pick (a), folded into design 1's DESIGN.md change.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **T11 counts requests, not attempts, so one failed try at an `each` judge can hold the item.** §2.5's T11 row counts "`judge.max_failures` different requests" ([DESIGN.md:329](../DESIGN.md#L329)), and the code does exactly that ([judge.rs:300-328](../../src/judge.rs#L300-L328)). But an `each` judge sends one request per match, and each excerpt's `match` section holds its `file:line` ([judge.rs:643-648](../../src/judge.rs#L643-L648)), which is part of the fingerprint. So:
   - one `gates` run in which three matches fail counts three, and
   - a line added above a failing match makes it a new request, though its code is unchanged.

   Reproduced: a stub with three `bail!("todo …")` lines, an `each` of `bail!\(` with `context_lines: 0`, and the default `max_failures`. `start` asked three requests. The first try added `use std::fmt;` at the top and wrote only `c`'s message. One `gates` counted three (`c1:src/lib.rs:3:works`, `…:6:works` and `…:9:works`), two of them `a` and `b`, unchanged apart from their line numbers. The second try fixed all three and the submit was held: `T11  judges failed 3 different requests since start, and judge.max_failures is 3, so the work may have been changed until a judge passed: c1:src/lib.rs:3:works, c1:src/lib.rs:6:works and c1:src/lib.rs:9:works`. The Why column says T11 is about "tweaking code, strings or comments until a judge passes", and this agent tried once. DESIGN.md's own example judge, the error-message one in §2.3.1, is an `each` judge over every `bail!`, `anyhow!` and `eprintln!`, so this is likely the first time any project uses one, and the harm is a false hold, a review I didn't need, never a wrong pass. No test has an `each` judge or a request with two failing questions under T11 (test gap 2). Fix: **(a)** count runs: each `gates` or `submit` that adds at least one new failed request counts once, keeping the requests in that run's entry, so an unchanged repeat still adds nothing. That changes the T11 row, `record_failures` and `t11`, and `failures.json`'s shape, which has no schema and isn't in the real store yet. **(b)** Leave `file:line` out of what T11 compares, which handles moved lines but not three matches failing at once. **(c)** Keep it and raise the default. I'd pick (a), before slice 15 builds on the count, with an `each` test of both cases in its first test commit.

2. **§3, §4.2 and §6 still describe T11 and `gates` as they were.** §3's `gates` row says it "changes nothing" ([DESIGN.md:438](../DESIGN.md#L438)), and it now writes `judge/failures.json` for an item in progress, as §2.4 says. §4.2 says `judge.max_failures` is how many failed requests "before a pass" hold the item ([DESIGN.md:582](../DESIGN.md#L582)), the T11 row's old wording, where the new row says "since `start`". §6's T11 row is security 1's. Found by reading. Low harm: §2.4 and §2.5, the sections the slice changed, are right. Fix: "changes nothing in the item, though it counts failed judge requests for T11 (§2.4)", "since `start`", and security 1's sentence. I'd fold them into design 1's DESIGN.md change.

## Slice 15 must decide

- **Whether a disputed fail counts toward T11.** `submit` counts every failed request before it decides whether the gates passed ([main.rs:2485-2491](../../src/main.rs#L2485-L2491)), so a `submit --dispute` adds the disputed request to T11's count, and the T11 row says nothing about disputes. The readme's Limits raises this. I'd count it, as now, since a dispute is still a fail the agent chose to argue, and say so in the T11 row, but slice 15 should choose and pin it with a test.
- **What `approve` and `reject` record for a T11 hold.** PLAN.md has them "record my decision against each held question", and `approve` counts T10 and T12 questions as passed. A T11 hold names its questions only inside `message`, since `Hold` has `trigger`, `message` and `files` and no refs ([item.rs:224-231](../../src/item.rs#L224-L231)), and `failures.json`'s refs are emptied by the next `start`. If decisions on T11 holds are to count per question, the hold needs its refs as data. Decide whether T11 holds are per question at all, or about the item, before slice 16's `judges` counts them.
- **Design 1 first.** If T11 is to count runs, change it before slice 15 builds disputes on the count, so `failures.json`'s shape changes once.
- **T12 in every pinned trigger list**, in TR-11's first test commit (process 1).

For slice 16:

- **`audit` can't see `failures.json` change.** It's reset at each `start`, left behind when an item is deleted, and removing it clears every count (security 2). Slice 16 should decide whether `audit` reads it at all, and say in §7 what it can't catch.
- **`judges` and the digest need T11's refs kept somewhere that lasts**: the hold in `verification.triggers` keeps only the message, and a reopen and `start` empties `failures.json`'s entry.
- **`started.checks` holds judges' entries too.** A reader must look at the criterion to know whether an entry is a check's or a judge's, as `t13` does ([triggers.rs:529-555](../../src/triggers.rs#L529-L555)).
