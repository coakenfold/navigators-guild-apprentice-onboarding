## Security

1. **One run can try several wordings at once, and counts once.** Per-run counting adds one entry however many new requests a run fails ([judge.rs:312-328](../../src/judge.rs#L312-L328)), and an `each` judge sends one request per match. So an agent can put several candidate wordings in the code as separate matches, commit them, run `gates` once, read from its output which one passed, and keep that one. Reproduced, with `max_failures: 2`, an `each` judge of `bail!\(` with `context_lines: 0`, and the stub's one `bail!("todo")`: `feat(XX-1): tries` added four functions with `"try 1"`, `"try 2"`, `"try 3"` and `"GOOD: run fix"`. One `gates` failed the stub's line, which was asked at `start`, and the three tries, and `failures.json` held one run with three requests and refs `c1:src/lib.rs:2:works` to `…:4:works`. `feat(XX-1): the work` kept only the passing wording, in the stub's place, and the submit was `in-progress → done`, verified automatically, with T11 quiet. The old per-request count would have counted three and held it. §2.5's Why says "every changed request is a fresh roll of the dice" ([DESIGN.md:329](../DESIGN.md#L329)), and a run can now hold many rolls. It needs a deliberate move, the tries are in the item's commits for `show --diff` and the digest, and review 1's security 1 already leaves the window before `start` open, which is cheaper still. So it's unlikely, but the harm is a wrong pass the record doesn't flag. Fix: **(a)** say it in §7's "Tries before `start` are free" bullet ([DESIGN.md:805](../DESIGN.md#L805)): after `start`, T11 bounds runs, not wordings, and one run can try several as separate matches. **(b)** Count a run once per question and matched line text that's new, which is close to counting requests again, and brings design 1 back. I'd pick (a), with design 1's change.

2. **A shelve, reopen and `start` empties the T11 count.** `start` writes the item's entry again with an empty `failed` ([judge.rs:277-292](../../src/judge.rs#L277-L292)), and an in-progress item can be shelved (with a clean tree and passing project checks), reopened and started again by the agent, with no human step. Reproduced, with `max_failures: 2`: XX-2's two failed `gates` runs left two entries, then `shelve`, `reopen` and `start` left `{"at_start": [one request]}`, and the passing work was `in-progress → done`, auto-verified, with T11 quiet. Without the shelve, the same two runs hold it, as `tr10_c3`'s tests show. The T11 row says "`start` starts the count again" ([DESIGN.md:329](../DESIGN.md#L329)), but nothing says an agent can reach that `start` on its own. The digest lists every shelve with its reason ([DESIGN.md:354](../DESIGN.md#L354)), and `start` grades the judges on the part-done code, so T13 holds it if they all pass by then. So it's unlikely and visible, and like security 1, a deliberate move. Fix: **(a)** add it to §7's "Tries before `start` are free" bullet, and have slice 16's digest mark a shelve of an item with a judge criterion. **(b)** Keep `failed` across a `start` that follows a shelve. I'd pick (a): (b) needs `record_start` to read history, and the digest already shows the move.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **Fixing an `each` judge's matches one run at a time is still held.** Review 1's design 1 found two causes of a false hold: several matches failing in one run, and a match whose request changes though its code doesn't. Option (a), which TR-51 took, fixes the first. The second is still there, and fixing a match one run at a time hits it, since each match's `code` section holds up to `context_lines` lines either side ([judge.rs:641-652](../../src/judge.rs#L641-L652)), the default being 12 ([config.rs:53](../../src/config.rs#L53)). Fixing one match changes every failing neighbour's request, and the run counts. Reproduced, in a project with no judge settings: four adjacent `bail!("todo")` lines, an `each` of `bail!\(`, and three `gates` runs, each after fixing one more line. Every run counted, and the submit with all four fixed was held: `T11  judges failed new requests in 3 runs since start, and judge.max_failures is 3, so the work may have been changed until a judge passed: c1:src/d.rs:2:works, c1:src/d.rs:3:works (2 runs) and c1:src/d.rs:4:works (3 runs)`. Line 4 was never touched until the last fix, and failed in three runs. §5 tells an agent to "run `tracker gates <ID>` to see what's left" ([DESIGN.md:741](../DESIGN.md#L741)), and §2.3.1's own example judge is an `each` over every `bail!`, `anyhow!` and `eprintln!`, with `context_lines: 4` ([DESIGN.md:156-157](../DESIGN.md#L156-L157)). Likely, the first time a project uses such a judge on a file with several messages close together. The harm is a false hold, never a wrong pass. Fix: **(a)** say it in the T11 row and §5's guidance: an `each` judge's fail counts again when nearby lines change, so fix every match it failed before running `gates` again. **(b)** Compare a failed request with earlier ones by its question and `match` line text, not its whole fingerprint, so a change in context alone isn't new. That stops counting tweaks to the code around a match, which the Why names. **(c)** Raise `max_failures`. I'd pick (a) now, since TR-11 and TR-12 have no judges, and decide on (b) once `judges` shows how often T11 holds are approved.

2. **Two of TR-51's `grep` phrases left repeated clauses in DESIGN.md.** §6's T11 row now reads "Judge failures on the open item before `start` aren't counted, so an agent can try the work there, and tries made on the open item before `start` are free (§7)" ([DESIGN.md:787](../DESIGN.md#L787)), which says the same thing twice. §7's forged-cache bullet reads "`judge/failures.json` is the same: removing `judge/failures.json` resets every item's T11 count" ([DESIGN.md:806](../DESIGN.md#L806)). Each holds the exact phrase criterion 6's check greps for. Found by reading. Cosmetic. Fix: drop "and tries made on the open item before `start` are free" from §6, and the second file name from §7, in a later DESIGN.md change. TR-51 is done, so its checks don't run again.
