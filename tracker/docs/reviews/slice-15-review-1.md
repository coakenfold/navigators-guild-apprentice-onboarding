## Verdict

Slice 15 does what PLAN.md asks. `submit --dispute <ref> --reason "…"` is repeatable, each ref paired with a reason checked as a `reject` reason is ([main.rs:2370-2406](../../src/main.rs#L2370-L2406)). When the judges were asked, a ref they didn't fail is refused with exit 1 before T11 counts anything, each disputed fail is taken out of G3's failures, and anything left refuses the submit as before ([main.rs:2553-2574](../../src/main.rs#L2553-L2574)). T12 fires on the disputed questions, between T11 and T13, and `review.disabled` can't switch it off. The held item keeps each question in `held_questions` with its request fingerprint, and `approve` counts a disputed fail as passed only for that same request ([main.rs:3792-3798](../../src/main.rs#L3792-L3798)), so a change made while the item waits is refused with G3. `approve` and `reject` both put the questions in their history entry. Slice 14's review points were taken: where a dispute lives, what it costs T11, T12 in every pinned list, and the DESIGN.md wording of TR-11's criteria 6 to 8. TR-11 was tracked as the rules ask: `5e16893` was committed 34 seconds before `start`, all eight checks failed then, every commit since is scoped to TR-11, and the user approved T1, T7 and T8 from a terminal, `human` at `4dce835`. `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` pass, and all **523 tests pass**, the count and split the readme gives.

Nothing here blocks the install: TR-12 has no judge criterion, so T11 and T12 never fire for it, and no item file changes shape unless a field is set. What matters most:

- **Security 1:** a `submit --dispute` refused with exit 1 asks every judge, says which way the disputed question went, and counts nothing, so an agent can try wording after wording with no T11 count, then submit the one that passed from the cache. Reproduced: four failing versions after `start`, then a fifth that passed, auto-verified with no run counted.
- **Design 1:** a held question records its ref, not the question, and the ref carries a criterion number `criterion remove` renumbers and an `each` match's `file:line`. Slice 16's `judges` counts "for each judge question", and has nothing stable to group by.
- **Design 2:** under `"auto_verify": false`, T10 holds with no unsure answer, so no question is recorded and no decision is counted, though §2.7 says each held question's is.
- **Bug 1:** `--reason`'s help says it's "for the --dispute before it", but the code pairs them by position. Reproduced, and unlikely.

TR-47, TR-48 and TR-50 are still open and deferred, as the readme says.

## Bugs

1. **`--reason`'s help says it goes with "the --dispute before it", but the code pairs them by position.** The help is at [main.rs:129-130](../../src/main.rs#L129-L130), and `submit` zips the two lists clap collects, which keep no record of where each flag was ([main.rs:2382](../../src/main.rs#L2382)). Reproduced: with a judge asking `works` and `clear`, both failed, `submit BM-1 --dispute c1:works --dispute c1:clear --reason "about clear" --reason "about works"` was held under T12 with `c1:works -> about clear` and `c1:clear -> about works` in `held_questions`. By the help, each reason followed its own dispute. I'd read the agent's evidence against the wrong question, and `judges` would keep it there. Unlikely, since §2.3.2, §5 and the usage line all show the pairs side by side, and the readme describes the positional rule correctly. Fix: **(a)** say it in the help: "the first --reason goes with the first --dispute, and so on". **(b)** Pair each `--reason` with the `--dispute` just before it on the command line, using clap's argument indices, and refuse any other order. I'd pick (a), since it's one line and the likely case already works, with a test of the odd order's pairing.

2. **During a judge outage, disputing the question is refused with "no judge question … was asked".** A failed call leaves no answer, so `check_disputes` finds nothing for the ref and refuses with exit 1, telling the agent to look up the ref in `gates` ([main.rs:2717-2720](../../src/main.rs#L2717-L2720)). Reproduced: with the fake judge exiting 1, `submit BM-1 --dispute c1:works --reason x` printed "BM-1 can't be submitted with that dispute: no judge question c1:works was asked", then pointed at `tracker gates BM-1` for the refs, while a plain `submit` said G3's judge couldn't be asked. The ref was right, and the real cause is hidden. §2.3.2 says a dispute "can only be checked against answers", and refuses for the earlier gate with exit 2 when the judges weren't asked ([DESIGN.md:256](../DESIGN.md#L256)), which fits a failed call too. Unlikely, since it needs an outage, and harmless beyond a wrong lead. Fix: **(a)** check the disputes only when every judge was answered: if G3 has a failure with no answer, refuse for it with exit 2, as for an earlier gate. **(b)** Add "or its judge couldn't be asked" to the message. I'd pick (a).

## Security

1. **A refused dispute is a free judge oracle that gets past T11.** `apply` asks every judge, then `check_disputes` refuses a ref that didn't fail before `count_failures` runs ([main.rs:2553-2561](../../src/main.rs#L2553-L2561)), as §2.3.2 and the T11 row now say ([DESIGN.md:256](../DESIGN.md#L256), [DESIGN.md:331](../DESIGN.md#L331)). The refusal says which way the disputed question went, and the answers stay in the cache. So an agent can dispute the question it's working on and then a ref nobody asked: `--dispute c1:works --reason x --dispute c9:nope --reason y` exits 1 every time, with "the judge passed c1:works", "the judge answered unsure to c1:works", or, when it failed, "no judge question c9:nope was asked". Reproduced, after `start`, with the default `max_failures` of 3: versions 1 to 4, each failing `works`, were each refused with the `c9:nope` message, version 5 with "the judge passed c1:works", and `judge/failures.json`'s `failed` stayed 0 throughout. A plain `submit` then printed `Criterion 1's judge: answered from the cache` and `BM-1: in-progress → done`, auto-verified. The same four tries through `gates` hold the item under T11. This is the move T11 exists to catch, "tweaking code, strings or comments until a judge passes", and §6 says T11 holds it ([DESIGN.md:792](../DESIGN.md#L792)). Unlike §7's limits on tries ([DESIGN.md:810](../DESIGN.md#L810)), it needs no stub, shelve or reopen, only a documented flag, and nothing in the item's record shows it. Even one dispute leaks a pass or an unsure answer for free. Slice 14's review 2 advised counting nothing on this refusal, "since nothing was submitted", and didn't foresee this: the judges were asked, and the agent learnt their answer. Likely only for an agent set on getting past a judge, but then it removes T11 altogether. Fix: **(a)** count the run before refusing, as a `gates` run counts: call `count_failures` before `check_disputes`, and change §2.3.2, the T11 row and `tr11_c2_a_dispute_refused_with_exit_1_counts_nothing_toward_t11` ([disputes.rs:349-357](../../tests/disputes.rs#L349-L357)) to say a refused dispute counts like a dry run. Changing that test fires T4, which only holds the fix item for me. **(b)** As (a), and also refuse a ref that names no judge criterion or question before any judge is asked, so a typo costs nothing. **(c)** Keep the refusal free, but make every exit 1 refusal the same and not name an answer. That leaves the agent nothing to learn but costs a useful message. I'd pick (a), and (b) if it stays small.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **A held question records its ref, not the question, so slice 16's `judges` has nothing stable to group by.** `HeldQuestion` has `trigger`, `ref`, `request`, `answer`, `reason` and `dispute` ([item.rs:250-259](../../src/item.rs#L250-L259)). §3 has `judges` report "for each judge question" how often I approved and rejected ([DESIGN.md:455](../DESIGN.md#L455)). The ref's criterion number is renumbered by `criterion remove`, its `file:line` changes with every match and every edit above one, and its question id is only unique within one judge file, so `c1:works` on one item and `c1:works` on another can be different questions, and one question can have many refs. The question's text is only in the item's current criteria, which a reopen and a `criterion set` can change after the decision. Found by reading. The readme's Limits raises it, but leaves it to slice 16, by which time real decisions could be recorded without it. Fix: **(a)** add the question's text (`ask`) to `HeldQuestion` now, and have §4.3 say `judges` groups by it, within a project. It's a new field with a serde default, so slice 15's fixtures still load. **(b)** Leave it, and have `judges` group by criterion and question id per item, which can't join one question across items. I'd pick (a), before slice 16 starts.

2. **Under `"auto_verify": false`, T10 holds with no question recorded, and `approve` and `reject` record T10 questions from different runs.** `t10` fires for `auto_verify: false` when every answer passed ([triggers.rs:503-506](../../src/triggers.rs#L503-L506)), but `unsure_questions` takes only unsure answers ([main.rs:2752-2758](../../src/main.rs#L2752-L2758)), so such a hold has no `held_questions`, and neither decision is recorded. §2.7 says the tool records my decision "when I approve or reject an item that a judge held under T10 or T12" ([DESIGN.md:378](../DESIGN.md#L378)), and that's such an item. Separately, `reject` records the submit's questions, while `approve` records the disputed ones plus the questions unsure at its own re-ask ([main.rs:3822-3824](../../src/main.rs#L3822-L3824)), though §4.3 says "`approve` copies them to `verification.held_questions`" ([DESIGN.md:695](../DESIGN.md#L695)). With unchanged work the cache makes the two the same, so this matters only when an answer changed. Found by reading. Likely for any project that sets `auto_verify: false`, which §4.2 offers to hold "every item a judge passed" ([DESIGN.md:585](../DESIGN.md#L585)), and `judges` would then count none of those items' decisions. Fix: **(a)** say in §2.7 and §4.3 that only disputed and unsure questions are recorded, so an `auto_verify: false` hold records none, and have `approve` copy the submit's T10 questions, as `reject` does. **(b)** Record every judge question under an `auto_verify: false` hold as T10, with its answer, so `judges` can count them. I'd pick (b) for the first half, since that setting exists so I look at every judged item, and (a)'s copy for the second.

3. **A held submit's JSON reports G3 as passed though its judge failed.** `take_disputed` removes the disputed failure from the report ([main.rs:2734-2749](../../src/main.rs#L2734-L2749)), and `gates_json` marks a gate `ok` when it has no failure ([gates.rs:119-120](../../src/gates.rs#L119-L120)). Reproduced: a held `submit --json --dispute c1:works` printed `{"gate": "G3", "ok": true}` beside `{"ref": "c1:works", "answer": "no", "result": "fail"}` in `judges`. The text says "Every gate passed but the disputed judge questions", and §2.3.2's example says "All other gates passed". [submit.schema.json](../../schemas/submit.schema.json) says the listed gates "passed, since a gate that fails refuses the submit", and §3 doesn't say what a disputed fail does to `gates`. An agent, or slice 16's digest if it reads `gates`, sees a G3 pass. Certain, and low harm, since `judges` and `item.held_questions` are right. Fix: **(a)** say in §3 and the schema that a disputed fail leaves G3 `ok`, with the fail in `judges` and in `item.held_questions`. **(b)** Report G3 with `"ok": false` and a `disputed` count. I'd pick (a), since a held item has passed every gate it could.

## Test gaps

1. **Nothing pins that a disputed fail counts toward T11.** The readme says so: moving `take_disputed` above `count_failures` would pass the suite. Security 1's fix moves the count again, so add a test that a held `submit --dispute` of a new failing request adds one run, and that a refused one does too once (a) is in.

2. **Only one of the input rules has a test.** [`tr11_c2_each_dispute_needs_its_own_reason`](../../tests/disputes.rs#L360-L372) covers a `--dispute` with no `--reason`. A ref disputed twice, a blank or over-long reason, a `--reason` with no `--dispute`, and the pairing order of bug 1 have none.

3. **`show`'s text for held questions, a T10 question recorded by `reject`, and a hold under both T10 and T12 have no test.** Each is a few lines in the existing helpers. Low.

## Slice 16 must decide

- **What a "judge question" is for `judges`** (design 1). Settle it before TR-12's `judges` test is written, and add the field in this round's fixes if (a) is taken.
- **Where `judges` reads decisions.** Every `approve` and `reject` history entry's `held_questions` is the record, and a reopen leaves history alone. A T11 hold records none, as §2.7 now says, and its refs live only in the hold's message and in `failures.json`, which `start` empties. `judges` should say that its counts are T10 and T12 decisions only.
- **What the digest shows of a dispute.** It lists each `approve` and `reject`. The disputed questions, with the model's and the agent's reasons, are in those entries, and an approved dispute is the line most worth a second look. Slice 14's review 2 also asked for a shelve and reopen of a judged item to stand out, and security 1's oracle leaves no line at all, so if it's left open, §7 should say so.
- **What `audit` checks of `held_questions`.** It's present only while an item is in review, so one on an item in another state, a T12 hold with no T12 question, or a T12 question with no T12 hold was written by hand.
- **The bootstrap.** Slice 15's binary will track TR-12. TR-12 has no judge criterion, so none of this slice's paths run for it, and its item file keeps slice 14's shape. If design 1's field is added, add it with a serde default and `skip_serializing_if`, as the others are.
