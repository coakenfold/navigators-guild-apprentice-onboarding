- **On TR's own items, every hold this binary places is right.** In a copy of the store, TR-6 gets T1 (a `capability`), T3 (`Cargo.lock` and `Cargo.toml`, for globset), T7 (1486 lines) and T8 (`docs/DESIGN.md`). I found no hold that fires wrongly in TR's normal flow.
- **TR-31's rule holds up.** For a commit not reachable from `started.head`, a test file is existing if `git cat-file -e` finds it there ([triggers.rs:85-88](../../src/triggers.rs#L85-L88)). It's right in a subfolder project, since `<sha>:<path>` takes the repository path the triggers already have, and a before-start fix to the item's own new test still holds nothing. It misleads only when the item's commits are rewritten after `start` (bug 2).
- **`approve` doesn't refuse what it should accept.** The simulated item's question, under `script`, listed its three holds at the `HEAD` it named, and an unscoped commit outside the root made while it waited changed nothing. TR-35's "(no longer fires)" lines are right, and `reject`, which passes the submit's holds as both lists, never prints one. The one new way for it to fail is a `started.head` that git no longer has, which makes it exit 3 (bug 3), and that needs a rebase and a prune.

## Bugs

1. **A misspelled `review`, or a `review` setting put directly under the project, is still ignored without a word.** TR-34 put `deny_unknown_fields` on `Review` ([config.rs:47-48](../../src/config.rs#L47-L48)), but `Project` ([config.rs:23-41](../../src/config.rs#L23-L41)) still skips unknown keys, on purpose, so that slice 12's per-project `judge` survives. So `"reveiw": {"risky_paths": […]}`, or `"risky_paths"` written beside `checks` rather than inside `review`, loads and leaves every setting on its default, which for T2 is never firing. Reproduced: with an unknown key under TR in a scratch store's config, `list` exits 0, while the same misspelling inside `review` exits 3. It fails open, as review 1's bug 1 did, and the user is about to write TR's `review` settings by hand, so it's the likeliest way left for a setting not to take effect. Still unlikely to happen: §4.2's example shows the nesting. Fix: **(a)** put `deny_unknown_fields` on `Project` too, with a `judge: Option<serde_json::Value>` kept as written, as `digest` is, and a test that a misplaced `risky_paths` exits 3. **(b)** Warn about unknown project keys and carry on. I'd pick (a), for the same reason review 1 did.

2. **"After start" means "not reachable from `started.head`", so rewriting the item's commits after `start` marks its test commit "after start", and can hold a before-start fix of its own new test.** `after` is `git rev-list <started.head>..HEAD` ([git.rs:366](../../src/git.rs#L366), [triggers.rs:72-75](../../src/triggers.rs#L72-L75)). A rebase or amend gives every rewritten commit a new SHA that `started.head` doesn't reach. Reproduced: XX-1's `test(XX-1)` commit changed `tests/old.rs` before `start`, and T4 said "(7dcf981 before start)". After `git rebase -i` reworded that commit, the same hold said "(c43cfd7 after start)". By reading the code, a second `test(XX-1)` commit before `start` that fixes the item's own new test, which holds nothing normally, would then fire T4, since the file exists at the old `started.head`. §2.5 says "a commit made after `start`" without saying how that's decided. It needs a branch rewritten while an item is in progress or in review, which the orchestrator does only to restack, so it's unlikely, and it errs towards more holds. Fix: **(a)** add a clause to §2.5: "after `start`" means not reachable from `started.head`, so rewriting the item's commits after `start` marks them all after it. **(b)** Decide by author date against `started.at`, which an agent can set. I'd pick (a).

3. **If `started.head` is gone from the repository, `gates`, `submit` and `approve` all exit 3 with a raw git error and no way forward.** `git::since` fails on an unknown base ([git.rs:366-372](../../src/git.rs#L366-L372)), and `triggers::run` returns the error before anything else. Reproduced: after the rebase in bug 2, `git reflog expire --expire=now --all` and `git gc --prune=now`, `gates` exited 3 with "`git rev-list 7dcf981…..HEAD` failed in …: fatal: Invalid revision range". Before TR-31 nothing read `started.head` after `start`, so this is new, and an item in review can then only be rejected and shelved, then reopened and started again, which the message doesn't say. It needs a rewrite and a prune of unreachable commits, which git does on its own only after weeks, so it's very unlikely. Slice 11's T14 reads the same range and will meet the same error. Fix: **(a)** catch it in `triggers::changes` and say what happened and how to recover: "`started.head` <sha> is no longer in the repository, so the commits after `start` can't be told apart. Shelve, reopen and start the item again." **(b)** Fall back to the before-start rule with a warning, which fires T4 less. I'd pick (a), since (b) fails open.

4. **T4 names at most 10 files, in commit order, so an after-start edit is the first to be cut to "N more".** `t4` lists files in the order of `existing_changed`, oldest commit first ([triggers.rs:285-297](../../src/triggers.rs#L285-L297)), and `file_list` keeps the first `git::LISTED_FILES`, which is 10 ([triggers.rs:200-206](../../src/triggers.rs#L200-L206)). So when a test commit before `start` updates ten or more existing test files, every file changed only after `start` is in "and 2 more", with no "after start" in the message, though `files` and `show --diff` still list it. Found by reading the code, and the simulated slice 11 item shows the order. A TR test commit touches three or four existing test files, so it's unlikely. Fix: list the files with an after-start commit first, a one-line sort before `named`.

## Security

1. **After `start`, an unscoped commit can delete an existing test so that the item re-adds it weakened, and this binary has no T14 to see the unscoped commit.** For a commit after `start`, an `A` only goes into `added` ([triggers.rs:96-98](../../src/triggers.rs#L96-L98)), even when the file exists at `started.head`. Reproduced: XX-1 started, `chore: tidy` removed `tests/old.rs`, `test(XX-1)` added it back with its assert gone, and `gates` passed with no hold. It's review 1's security 2 moved after `start`, where §7 says T14 catches it. From slice 11's binary on it does, but this binary judges TR-7 without T14. It needs a deliberate two-step, so it's unlikely. Fix: **(a)** in `changes`, for a commit after `start`, count an `A` of a path that exists at `started.head` as a change to an existing file, a few lines. **(b)** Leave it to T14, and read TR-7's unscoped commits by hand, which the bootstrap rule asks for anyway. I'd pick (b), since only TR-7 is exposed and its record is already read by hand.

2. **Lines that switch an existing test off are added lines, so T4 doesn't see them, and the readme says the tests "can't be weakened" after `start`.** Reproduced: adding `#[ignore]` above an existing test, or `return;` as its first line, after `start` passed `gates` with no hold. §2.5's T4 row says this, with `test.skip` as its example, and leaves it to the digest, which comes in slice 16. In TR a criterion check such as `cargo test --test risky_changes tr_31_c1` still exits 0 when its test is ignored, with "0 passed; 1 ignored" in the saved output. But the readme says in [What's in this slice](../slice-10-readme.md#whats-in-this-slice) and [Decisions worth knowing](../slice-10-readme.md#decisions-worth-knowing) that an item "can't weaken them after it without firing T4", which is more than the code gives. Likelihood: low for a deliberate dodge. Fix: **(a)** reword the readme's two sentences to "can't change or remove a line of them, or delete them, after it without firing T4", and say what added lines can still do. **(b)** Teach T4 a few markers such as `#[ignore` and `.skip(`. I'd pick (a): (b) is a list that never ends, and slice 16's digest is the design's answer.

## Where the code and DESIGN.md disagree, or the design is unclear

1. **"before start" says when a test was edited, not that the edit was sanctioned, and the readme teaches the user to read it as expected.** The mark is accurate. But the readme says the message "tells that sanctioned edit from one made after it" ([How it works](../slice-10-readme.md#the-triggers)) and that TR-7's hold "reads as the expected hold" ([Limits](../slice-10-readme.md#limits-and-what-later-slices-change)). A `test(TR-n)` commit before `start` can weaken an existing test in the same commit that updates a pinned list, and it gets the same "before start" mark. Every slice item from TR-7 on will show the mark, so the habit of approving it on sight is certain. A weakening hidden there is unlikely, since it needs intent. Fix: **(a)** say in §2.5 and the readme that a before-start edit isn't vetted, so `show --diff`'s lines for T4's files are worth reading whichever side of `start` they're on. **(b)** Add each commit's removed-line count to the mark, such as "09bd837 before start, 1 line removed". A one-line weakening reads the same, so it's a hint, not proof. I'd pick (a).

2. **§2.5's and §3's T4 examples don't match the message the code prints.** Both read `existing test modified: tests/bookmarks.spec.js` ([DESIGN.md](../DESIGN.md#25-review-triggers-does-it-need-a-human), lines 345 and 498). The code prints `existing test file modified: tests/bookmarks.spec.js (1a2b3c4 after start)`, and §3's `holds` have no `files`. TR-36 fixed T3's examples, review 1's design 3, and left T4's beside them. It's only text. Fix: change both T4 examples to the code's message, and add `files` to §3's two holds.
