Setting up

Done once per project.

01You

Register a project

One store in ~/.tracker holds every project. A project needs a key, a name and a root to start. The checks and review policy live in config.json.

  • Project checks run on every submit (G4), whatever the item is about.
  • source_paths adds *.js to the src/** default, because this app keeps app.js at the top level and the rest of its code in src/. It decides which files count as source code, so adding a new one holds the item (T1).
  • There are no judge settings here. Judges run only for items whose criteria ask for one, and the defaults suit most projects.
  • Two lines in Claude Code's settings let agents run tracker without asking you each time, and stop its edit tools from touching the store.

02You

A couple of weeks in, BM-1 to BM-11 already exist. A /decompose plan gives you three new slices. Each slice's outcome becomes a title, and its "Done when" lines become criteria.

  • Running from inside ~/code/bookmarks makes BM the default project, so there's no --project.

03Agent

Write failing tests, then start

Following the instructions in CLAUDE.md, the agent reads the item, turns each manual criterion into a script check, writes the tests those checks run, commits them as test(BM-12): …, and starts.

  • start runs every check once and expects it to fail, because the feature doesn't exist yet. A check that already passed would hold the item later (T13, scene 12).
  • "Failed at start, passed at submit" is what makes a check mean something. It's printed in the record in scene 6.
  • start takes a fingerprint of the criteria. Changing them after this point holds the item (T5).
  • Every criterion has a check, so T6 will stay quiet and nothing here will need you.

04Agent

Ask "what's left?"

The agent writes the code, commits with the item ID as the scope of each message, and runs gates. This dry run shows what a submit would refuse, without changing anything.

  • Cheapest first. The static gates failed, so the 52 seconds of Playwright never ran.
  • Every problem is listed at once, so the agent can fix them in one pass.
  • The scope in feat(BM-12): … is how the tool finds this item's changed files. A commit since start with no item scope would hold the item (T14).
  • Script criteria need no evidence note: each check's own output is the proof, saved at done. G2 only asks manual criteria for one. Adding test cases to an existing spec file doesn't fire T4 either; only changing or removing test lines does.
  • The working tree must be fully clean, including no untracked files, so the commit holds everything the tests ran with.

05Agent

The full suite catches a regression

Static gates pass now, so the scripts run. BM-12's own checks pass, but the project's full suite doesn't: the new code broke "Bookmarks persist across reloads", which BM-10 already took to done.

  • Project checks run on every submit, whatever the item is about (G4). That's what stops later work from breaking done items.
  • The failure shows the command, the exit code and the last lines of output, so the agent can go straight to the cause.
  • BM-12's criteria are all tests, so no judge runs and the model is never called. Judges run only for items whose criteria ask for one (scene 9).
  • A refusal changes nothing. BM-12 stays in progress, and nothing here needs you.

06Agent

Submit: auto-verified

Every gate passes and no review trigger fires: no new file, no new dependency, no test edited, criteria unchanged since start. The item goes straight to done with nobody asked.

  • No judge ran. Both criteria are tests, so BM-12 reached done without the model.
  • The verification record is the proof: which commit, which checks, and what they printed. An item with a judge also records each answer and the model that gave it.
  • Each check's last lines of output are saved at done, so the record shows which tests actually ran, not what anyone claims ran.
  • refs/tracker/BM-12 keeps that commit, even if its branch is rebased or squashed, so the tests as they ran can still be read.
  • You'll see BM-12 later in the weekly digest, not now.

Gates passed, but something risky happened.

07Agent

A risky change is held

BM-14 adds fuzzy search with a new library and edits an existing test. The work passes every gate, but two triggers fire, so the item waits for you.

  • A held submit still exits 0. Being held isn't an error; the output says where the item ended up.
  • The triggers come from git history, not from what the agent says: package.json and a file under tests/ are among BM-14's changed files.
  • An edited test may no longer prove the done items that relied on it, which is why T4 holds. G4 already ran the full suite, so nothing done is broken: what you check is whether the edit weakened a test.
  • The agent can't approve its own work. It stops and reports.

08You

Clear the inbox

tracker review is the one command you need to remember. It lists what's waiting and why. You read BM-14's change with show --diff and approve it.

  • show --diff puts the files that fired a trigger first, so the test edit behind T4 is the first thing you read.
  • approve runs the gates again first, so nothing that broke since the submit gets through.
  • You confirm by typing the item ID. That needs an interactive terminal, which an agent's shell isn't.
  • Deciding BM-14 also frees the project. Only one item at a time can be in progress or in review (G1), so BM-13 couldn't start until now.

09AgentYou

A judge for what tests can't measure

BM-13's first criterion is a normal test. Its second asks whether every import error is helpful, which a script can't decide. So the agent writes a judge: two short yes/no questions, asked once for each error in src/import.js. One answer comes back unsure, and you send the item back with a concrete note.

  • each splits the work in code: three matches, two questions each, and every answer must pass. A pattern that matches nothing is refused, because a judge with nothing to grade would pass without asking anything.
  • The judge runs at start too, against the old messages. It should not pass yet. If it did, its questions couldn't tell bad messages from good ones (T13).
  • One answer comes back unsure: the excerpt doesn't show enough to decide. That's not a fail, so the gates pass. It's not proof either, so T10 holds the item.
  • The excerpt and the model's reason come with the hold, so you can decide without opening the file.
  • Your reject covers this submit only. v1 saves no rulings, so if the agent resubmits the same code, the cached unsure answer holds it again.

Day 3 · When the judge is wrong

The model fails good work, and the agent can't overrule it alone.

10AgentYou

Dispute a wrong fail

The agent reworks BM-13 using your note. Instead of repeating the next step in every message, app.js:210 now prints it after every ImportError, so the message at :57 only names the problem. The judge sees a few lines around :57, not app.js, and answers no to suggests_next_step, confident and wrong about what the user sees. The agent can show it's wrong, so it disputes the answer.

  • A fail refuses the submit. Before disputes existed, that was a dead end, because the item could never reach review.
  • --dispute can't pass anything. It moves the decision from the model to you, under T12.
  • A judge sees only its excerpt. A next step that lives somewhere else, here in app.js, is exactly what it can miss.
  • Your approval covers this submit only. v1 saves no rulings, so if BM-13 ever comes back with the same code, it needs the same dispute.
  • Your decision counts toward tracker judges. If suggests_next_step keeps getting overruled, the question itself needs fixing.

End of the week · Checking the checker

Auditing what passed without you.

11You

Audit the weekly digest

Each project's digest lists everything that reached done without you since you last acknowledged it, plus anything an agent shelved. Items that passed on a judge come first, because that's where a wrong pass is most likely.

  • BM-11's judge said yes to both questions, and it was wrong. An answer carries no measure of doubt, so a wrong yes looks like any other (§7). That's why the digest exists.
  • reopen sends it back with your reason. If it comes back with unchanged code, T13 holds it, because its judge already passes at start. The better fix is a test instead of a judge.
  • Outside a project folder, tracker digest shows every project's digest. digest ack --project clears one and resets its overdue clock.

12YouAgent

Guardrails in action

Short exchanges from across the week where the tool says no, and what it suggests instead. Most map to a row in the trust table in §6.

  • Moving the goalposts is allowed but never quiet: the item will be held (T5). That includes dropping one of your criteria before starting.
  • A dispute only works on a question that actually failed, so it can't be filed in advance.
  • A check that passes before the work is allowed but flagged (T13). cargo test with a filter that matches nothing is the classic case.
  • Shelving work that's under way must leave the project checks passing. The item's tests still fail, and left on the branch they'd fail the next item's submit (G4), so the agent reverts them first.
  • Only you can delete, and the prompt says what goes with it. An item that won't be done is shelved by the agent, then deleted by you.
  • audit catches a hand-edited status after the fact. It can't prevent one.

The agent's view

One item from prompt to done, as Claude Code runs it.

13Agent

One whole session

You give one instruction. Every call after it is the agent's, through Claude Code's tools. The only thing you read is the report at the end.

  • The allow rule means none of these calls needs your approval.
  • --json gives the agent fields to act on: the criteria, the start results, and each failure's gate and message, plus ref, answer and reason when a judge fails.
  • Both criteria can be tested, including the toast text, so no judge. Judges are for what a test can't measure.
  • When it reaches for the item file to tick off a criterion, the deny rule stops it. Nobody ticks criteria: the checks prove them at submit.
  • The full suite (G4) catches an existing test the feature broke. Changing that test would hold the item (T4), and the test is right, so the agent fixes the code.
  • BM-17 auto-verified, so you'll next see it in the digest.

What the mockup surfaced

Decisions it settled

Writing concrete screens exposed twelve gaps in the design doc. Each one is now decided in DESIGN.md.

A judge that fails good work is no longer a dead end

The agent can dispute the fail, which holds the item for you under T12. Your approval decides that submit, and tracker judges counts it against the question (scene 10).

§2.3.2 · T12 · §2.7

A wrong pass can't come back unchanged

reopen sends a done item back with a reason. If it returns with unchanged code, T13 holds it, because its checks or judge already pass at start (scene 11).

§2.6 · T13

The check is the evidence

Script and judge criteria need no evidence note: their own output is the proof, saved at done. Only a manual criterion gets a note, and it's left out of the T5 fingerprint because it can only be written once the work exists (scene 4).

§2.3 · G2 · T5

The inbox shows the change

tracker show <ID> --diff lists the item's commits and diff, with the files that fired a trigger first, so you never leave the tool to review a hold (scene 8).

§3 Looking around

Triggers are re-checked on every submit

After a reject, the resubmit is held again for every trigger that still applies, because the work changed since you looked. None of your earlier decisions carry over.

§2.5

The record shows which tests ran

Each check's command, result, duration and last 20 lines of output are saved at done, so tracker show prints what actually ran. refs/tracker/<ID> keeps the commit through rebases, and G5 refuses untracked files, so the commit holds everything the tests ran with (scene 6).

§2.3 · G5 · §2.7

Checks must fail before the work

start runs every check and expects a fail. One that already passes, like a filter matching no tests, holds the item under T13 (scene 3, scene 12).

§2.4 · T13 · §5

Changing a proving test is visible

T4 ignores pure additions and holds any change to an existing test, because it may be another item's proof. G4 runs the full suite on every later submit, so a change that breaks done behaviour is refused (scene 5, scene 7).

T4 · G4 · §6

Your criteria can't be quietly rewritten

The criteria text is fingerprinted at create. An agent can attach checks and add criteria, but rewording or dropping yours holds the item (T5), even before start (scene 12).

§2.1 written · T5

Judges must have something to grade, and must not pass yet

A judge whose pattern matches nothing fails instead of passing empty. Criterion judges also run at start, and one that already passes is held like a check that does (scene 9).

§2.3.1 · §2.4 · T13

Agents never edit tracker files

Items change only through tracker commands. Claude Code's settings allow tracker without asking and deny its edit tools on the store (scene 1, scene 13).

§3 Interface · §5 settings

Output agents can parse

Every command takes --json. The text can change freely, but the JSON fields are an interface, with refs and hold reasons as data (scene 13).
